# Plan 2.0 — Modal runtime for training and evaluation

> **Scope:** extend the runtime abstraction so that full experiments can run on
> Modal GPUs. After this plan, the entire citation-forecast pipeline —
> preprocess, describe, engineer, train, and eval — can run either locally or
> on Modal with a single `--runtime modal` flag.
>
> **Prerequisites (do not start without them):** plans 1.1 (**including its §8
> experiment env-injection — `build(runtime, env)`**), 1.2, and 1.3 are
> complete. The `Runtime` protocol, `LocalRuntime`, `ModalRuntime`,
> `build_runtime`, `ModalVolumeSource`, the optional `modal` packaging extra,
> and the `[runtime]` config section all exist already. This plan adds **only**
> train/eval on Modal; it must not re-litigate the data pipeline.
>
> This release is deliberately promoted to **v2.0** because it moves the core
> training/evaluation loop into the cloud, introduces new production
> infrastructure (Modal images, volume-backed checkpoint scratch, remote MLflow
> logging), and changes the project’s operating model from “local CLI tool” to
> “hybrid local/cloud ML platform”.

---

## 1. Goal

`citef train` and `citef eval` support `--runtime modal`:

- **local** (default): runs the existing PyTorch training loop on the local
  machine, saving checkpoints and MLflow artifacts locally.
- **modal**: runs the same training/evaluation loop inside a Modal GPU
  container, reading data from Modal volumes, writing checkpoints through to
  MLflow, and logging to the configured MLflow tracking server.

A single `--runtime modal` flag (overriding `[runtime].default`) switches
modes. `train.py` and `eval.py` do not branch on the runtime string; they
delegate to `runtime.run_train(...)` and `runtime.run_eval(...)`.

---

## 2. Why this is v2.0

The criteria from plan 1.2 for promoting Modal work to a major version are now
met:

1. **Core loop moves to the cloud.** Training and evaluation are the heart of
   the project; running them remotely is a qualitative change, not just an
   incremental feature.
2. **New production infrastructure.** We need Modal images that bundle the full
   project, volume-backed checkpoint scratch, remote MLflow integration, and
   experiment-file transport into the container.
3. **Artifact and reproducibility changes.** Checkpoints, experiment files, and
   MLflow artifacts must behave consistently across local and Modal runs.
4. **Public promise.** v2.0 signals that citation-forecast is now a hybrid
   local/cloud system, not merely a local CLI with optional remote preprocessing.

---

## 3. Principles

| # | Principle |
|---|---|
| P1 | **Same experiment file everywhere.** An experiment module runs unchanged on local or Modal; machine-dependent values arrive via the injected `Env` (plan 1.1 §8), never via module-level imports. No Modal-specific code inside `src/config/experiments/`. |
| P2 | **Runtime owns execution.** `train.py` and `eval.py` only parse CLI args and call `runtime.run_train(...)` / `runtime.run_eval(...)`. No `if runtime == "modal"` branches. |
| P3 | **Checkpoint continuity via MLflow.** MLflow artifacts are the *canonical* checkpoint store — the existing `MlflowCheckpointProcessor` already uploads on save and downloads on load. The Modal checkpoint volume is in-container scratch/cache only. A checkpoint saved on Modal resumes locally (and vice versa) with **no new code paths**. |
| P4 | **Reproducible env.** The Modal image is built from the same dependencies and source as the local environment. |
| P5 | **Backward compatibility where possible.** Local behaviour is unchanged, including on machines without Modal credentials or the `modal` package. |
| P6 | **Client-created runs.** The MLflow run is created on the client (which owns run naming/parenting) and resumed inside the container by `run_id`. |
| P7 | **Fire-and-forget dispatch.** Long Modal jobs are `.spawn()`ed; the CLI returns immediately with the MLflow run id and the Modal FunctionCall id. |

## 4. How this fulfils `plans/notes.md`

The notes doc defines the purpose of the 2.0 point:

> *"Runtime is an interface that determines everything relevant to the
> execution of the code ... switch out the runtime object and have the code run
> elsewhere ... the code running remains identical, so that local testing
> replicates online deployment and all it takes is a cli argument/flag."*

Concretely, in this plan:

- **Runtime determines execution.** Device/compile arrive via `RunContext`;
  machine paths/credentials arrive via `Env`; dispatch (in-process vs. Modal
  container) is owned by the `Runtime` implementation. Nothing execution-
  relevant lives outside these three objects.
- **Identical code.** `run_train_pipeline` / `run_eval_pipeline` (§8/§9) run
  unchanged locally and inside the container. The *entire* difference between
  venues is the `Env` mapping in §7.3 and the dispatch wrapper in §8.3 —
  experiment files are byte-identical (P1).
- **Single flag.** `--runtime modal` (or `[runtime].default = "modal"`) is the
  whole user-facing switch, for every app.
- **Modal first, not Modal only.** The protocol leaves room for other cloud
  providers behind the same `Runtime` interface; only `ModalRuntime` is
  implemented in the v2 line.
- **Distributed GPU training/eval** (the final line of notes.md) is explicitly
  deferred to `plans/2.2.md`; the pipeline split in this plan is designed to
  make that refactor possible without touching apps or experiment files.

## 6. Runtime protocol additions

Extend the `Runtime` protocol from plans 1.2/1.3:

```python
@dataclass(frozen=True, kw_only=True)
class RunResult:
    run_id: str
    status: str                      # "completed" | "spawned"
    checkpoints: list[str]           # checkpoint artifact paths/URIs produced
    metrics: dict[str, float]        # final summary; empty when spawned
    modal_function_call_id: str | None = None


class Runtime(Protocol):
    def get_source(self, root: str | Path, name: str) -> DataSource: ...
    def get_embedder(self, key: str, **kwargs: Any) -> TextEmbedder: ...
    def maybe_download(self, source: DataSource) -> Path: ...
    def maybe_upload(self, source: DataSource, local_path: Path) -> None: ...
    def run_preprocess(self, job: PreprocessJob) -> DataSource: ...
    def run_describe(self, job: DescribeJob) -> None: ...
    def run_engineer(self, job: EngineerJob) -> DataSource: ...
    def run_train(self, job: TrainJob) -> RunResult: ...
    def run_eval(self, job: EvalJob) -> RunResult: ...
```

`RunResult` lets the caller log what happened (or, for spawned Modal jobs,
print how to follow the run).

## 7. Experiment portability (the notes.md core)

### 7.1 Contract

The experiment contract is `build(runtime: RunContext, env: Env) ->
Experiment`, established in plan 1.1 §8. Experiment files contain no machine
paths, no `config.toml` reads, and no `config.env` imports. The dataset
*name*, model, strategy, tracker, and processor *choice* stay in the
experiment file (plan 1.0 B1/E3); only machine-level locations arrive via
`Env`.

### 7.2 Experiment file transport (Option A)

- The app reads the local experiment file at the resolved module path and puts
  its raw bytes on the job (`experiment_source: bytes`).
- The pipeline writes the bytes to a temp file and calls
  `load_experiment_from_path(path, runtime, env)` — identical in both runtimes.
- Experiment files are a few KB; volume transport (Option B) is only
  reconsidered if that changes. Do not implement Option B in 2.0.

### 7.3 In-container Env derivation

`ModalRuntime` maps the client `Env` onto the volume mounts **before
spawning**:

```python
container_env = Env(
    tracking_uri=modal_tracking_uri,                    # validated in §10.5
    raw_loc=Path(f"/modal/{raw_volume}"),
    staged_loc=Path(f"/modal/{staged_volume}"),
    artifact_loc=Path(f"/modal/{checkpoint_volume}"),   # scratch only (P3)
)
job = dataclasses.replace(job, env=container_env)
```

`LocalRuntime` passes the `Env` through unchanged. This mapping is the entire
difference between the two execution venues.

### 7.4 No job-level `data_source`

Earlier drafts of this plan carried `data_source: DataSource` on
`TrainJob`/`EvalJob`. It is removed: dataset *identity* (name) is
experiment-relevant and lives in the experiment file (B1); dataset *location*
is machine-level and arrives via `Env` (§7.3). `DataSource` objects remain the
boundary for the data-pipeline jobs (plans 1.2/1.3) and for explicit
`maybe_upload` staging (§10.4).

## 8. Train pipeline

### 8.1 `src/training/pipeline/train.py`

```python
@dataclass(frozen=True, kw_only=True)
class TrainJob:
    experiment_name: str        # module name (root CLI/toml resolution)
    experiment_source: bytes    # raw experiment file bytes (§7.2)
    run_name: str
    run_id: str                 # filled by the runtime wrapper (P6) via replace()
    parent_id: str | None
    start_epoch: int
    compile: str
    fullgraph: bool
    load_id: str
    load_epoch: int | None
    model_only: bool            # J3: optimizer/scheduler restore is the default
    subsample: int | None
    env: Env


def run_train_pipeline(
    job: TrainJob, progress: ProgressBars | None = None
) -> RunResult:
    ...
```

### 8.2 `run_train_pipeline` steps (identical local/Modal)

1. Write `job.experiment_source` to a temp file.
2. Build `RunContext(device=<cuda if available else cpu>, dtype=torch.float32,
   compile_mode=job.compile, fullgraph=job.fullgraph, subsample=job.subsample)`.
   Device selection is an execution detail and happens inside the pipeline —
   the job never carries a device.
3. `exp = load_experiment_from_path(path, runtime, job.env)`.
4. If `job.compile`: `exp.model.compile(mode=job.compile,
   fullgraph=job.fullgraph)` (moved here from the app).
5. Resume when `job.load_id` is set: `exp.checkpoints.load(CheckpointRef(
   run_id=job.load_id, epoch=job.load_epoch))`; load model always; restore
   optimizer/scheduler via `strategy.load_optimizer_state` unless
   `job.model_only` (plan 1.0 J3).
6. `with mlflow.start_run(run_id=job.run_id):` — resume the client-created run
   (P6) — construct `Engine(experiment=exp, runtime=runtime,
   progress=progress)` and call `engine.fit(start_epoch=job.start_epoch,
   run_id=job.run_id)`.
7. Return `RunResult(run_id=job.run_id, status="completed",
   checkpoints=[...], metrics=<final epoch metrics>)`.

### 8.3 Runtime wrappers (own the run lifecycle — P6)

Both runtimes perform these client-side steps first:

1. Import the experiment module client-side (module level only — **do not**
   call `build`) to read its `experiment_name` string.
2. `mlflow.set_tracking_uri(job.env.tracking_uri)`;
   `mlflow.set_experiment(experiment_name)`.
3. Create the run via the low-level client —
   `MlflowClient().create_run(experiment_id=..., run_name=job.run_name,
   parent_run_id=job.parent_id)` — so the fluent active-run stack stays free
   for the pipeline to resume by `run_id`. Log params plus the experiment-file
   and model-source-file artifacts client-side (plan 1.0 B4).
4. `job = dataclasses.replace(job, run_id=run.info.run_id)`.

Then dispatch differs — and this is the *only* branch:

- `LocalRuntime.run_train`: call `run_train_pipeline(job,
  progress=build_progress_bars(...))` in-process; return its completed
  `RunResult`. (Progress-bar construction moves from the app into the runtime
  wrapper — an internal change, no CLI change.)
- `ModalRuntime.run_train`: validate the tracking URI (§10.5), derive the
  container Env (§7.3), `.spawn()` the remote entry point (§10.2), print the
  MLflow run id + Modal FunctionCall id, and return `RunResult(status=
  "spawned", run_id=..., modal_function_call_id=...)`.

### 8.4 App changes (`src/apps/train.py`)

1. Keep every existing CLI flag; add `--runtime` (default from
   `[runtime].default`).
2. `env = load_env(overrides)`; `runtime = build_runtime(flag, env, config)`.
3. Resolve the experiment module name from the root `ctx.obj` (as today) and
   read the file's bytes.
4. Build `TrainJob` (without `run_id`); `result = runtime.run_train(job)`.
5. Print/log the result — for Modal: run id, FunctionCall id, and how to
   follow the run (MLflow UI; `modal.FunctionCall.from_id(<id>).get()` to
   block until done).

No runtime-specific branches; the app no longer calls `mlflow.start_run`,
builds an `Engine`, or touches checkpoint processors.

## 9. Eval pipeline

### 9.1 `src/training/pipeline/eval.py`

```python
@dataclass(frozen=True, kw_only=True)
class EvalJob:
    run_id: str                  # training run to evaluate
    epoch: int
    prefix: str
    start_date: datetime | None
    end_date: datetime | None
    interval: int | None
    interval_unit: str
    experiment_name: str | None  # eval runs land in "<name>-EVAL" by default
    eval_run_id: str             # client-created eval run id (P6)
    clean_up: bool
    env: Env


def run_eval_pipeline(job: EvalJob) -> RunResult:
    ...
```

### 9.2 `run_eval_pipeline` steps (identical local/Modal)

1. Build the `MlflowCheckpointProcessor` from `job.env`. Call
   `experiment_file_exists(run_id=job.run_id)` **first** — hard crash
   `"No experiment file found for run <id>"` if missing (plan 1.0 J1; fail
   fast, no hanging download).
2. `download_experiment_file` to a local temp dir;
   `load_experiment_from_path(path, runtime, job.env)`.
3. Load the checkpoint (`CheckpointRef(run_id=job.run_id, epoch=job.epoch)`)
   into the model; `model.eval()`; keep today's cuda compile behaviour.
4. `with mlflow.start_run(run_id=job.eval_run_id):` run the sliding-window loop
   **lifted verbatim** from today's `apps/eval.py`
   (`dataset.with_window(...)` + per-window `DataLoader` rebuild), driving
   `engine.eval_epoch(epoch, loader=window_loader)`.
5. Prediction exports: write to a local temp dir per window (as today, but
   under temp instead of `env.staged_loc / "eval" / ...`) and
   `mlflow.log_artifacts(export_dir, artifact_path=f"exports/{window_year}")`.
   **MLflow artifacts are the export channel on both runtimes** — on Modal
   there is no `staged_loc` to write to, and artifacts are downloadable from
   anywhere.
6. Honour `job.clean_up` for the temp dir; return
   `RunResult(run_id=job.eval_run_id, status="completed", metrics=<last
   window summary>)`.

### 9.3 App changes (`src/apps/eval.py`)

Mirror §8.4: parse (existing flags + `--runtime`), build `env`/`runtime`/job,
delegate. The eval MLflow run is created by the runtime wrapper (the
`<experiment_name>-EVAL` naming logic moves with it) and its id passed in as
`job.eval_run_id`.

## 10. Modal runtime implementation

### 10.1 Modal training GPU class

```python
@modal.cls(
    gpu=modal_cfg.train_gpu,          # e.g. "A10G"
    image=train_image,
    volumes={
        f"/modal/{staged_volume}": staged_volume,
        f"/modal/{checkpoint_volume}": checkpoint_volume,
    },
    timeout=modal_cfg.timeout,        # long-running training jobs (24h default)
    enable_memory_snapshot=True,
    experimental_options={"enable_gpu_snapshot": True},
)
class ModalTrainingGPU:
    @modal.enter(snap=True)
    def setup(self):
        # Optional: preload common model weights or tokenisers
        ...

    @modal.method()
    def train(self, job: TrainJob) -> RunResult:
        return run_train_pipeline(job)        # progress=None in-container

    @modal.method()
    def eval(self, job: EvalJob) -> RunResult:
        return run_eval_pipeline(job)
```

- A single GPU class for train and eval shares the image and volume mounts.
- GPU snapshot flags follow the working precedent in `production/service.py`.
- **Caveat:** `torch.compile` can break snapshot restore. When snapshotting is
  enabled, dispatch with `job.compile == ""`. This is a dispatch decision —
  experiment modules never adapt to the runtime (P1).

### 10.2 Dispatch style (P7)

- Entry points are invoked with `.spawn()`; the client prints the FunctionCall
  id and returns immediately. A detached 24h training run survives client
  disconnect.
- `.remote()` (blocking) is kept only for debugging/smoke-sized runs.
- Plan 2.1 (monitoring/retries) polls `modal.FunctionCall.from_id(...)` using
  `RunResult.modal_function_call_id` as the join key; plan 2.3 adds live
  progress reporting.

### 10.3 Modal image

```python
train_image = (
    modal.Image.debian_slim(python_version="3.13")
    .pip_install_from_pyproject("pyproject.toml")
    .add_local_dir("src", remote_path="/root/src")
    .env({"PYTHONPATH": "/root/src"})
)
```

- Flat src-layout: `src/` on `PYTHONPATH` makes `apps`, `config`, `data`,
  `models`, `training`, `utils`, `builders` importable exactly as locally
  (same approach as plan 1.2 §9.2).
- Dependencies come from `pyproject.toml` (torch, transformers, polars, mlflow,
  scikit-learn, typer, seaborn); the project itself is not pip-installed.
- `config/config.toml` is deliberately **not** in the image — jobs carry their
  `Env`.

### 10.4 Checkpoints, staging, artifacts

- Canonical checkpoint store = MLflow artifacts (P3). In-container,
  `MlflowCheckpointProcessor.artifact_loc` is the checkpoint-volume mount: it
  is scratch for `torch.save` + the upload source for `mlflow.log_artifact`,
  and nothing more.
- Local resume from a Modal run needs **no new code**: the same processor
  downloads the artifact from MLflow. Verified in §13.
- The staged dataset must exist on the staged volume before training (produce
  it with `citef preprocess --runtime modal` from plan 1.2). The container
  fails fast, naming the resolved missing path, otherwise.
- Optional convenience flag: `citef train --runtime modal --stage-dataset
  <name>` uploads a local staged dataset directory via
  `runtime.maybe_upload(...)` before spawning.
- Train/eval pipelines need **no** in-container `Runtime` (unlike the 1.2/1.3
  data pipelines): sources resolve through the injected `Env`.
  `_in_container_runtime()` remains exclusive to the data pipelines.

### 10.5 MLflow from Modal

- Validate **client-side, before spawning**: reject loopback tracking URIs
  (`127.0.0.1` / `localhost`) with a clear message that Modal runs need a
  network-reachable URI.
- `[runtime.modal].tracking_uri` (optional) overrides `env.tracking_uri` when
  deriving the container Env (§7.3).
- Credentials move to Modal secrets in plan 2.1 (F-29).

## 11. Engine headless mode (concrete change)

`engine.py` cannot stay untouched, as earlier drafts claimed — its constructor
currently *requires* rich progress bars, which are meaningless in a headless
container:

1. `Engine.__init__(..., progress: ProgressBars | None = None)`; store the
   value, and only call `add_task` when it is not `None`.
2. Guard every `reset`/`advance` call behind `if self._progress is not None`.
   Keep the guards small and centralised — plan 2.3 replaces them with a real
   `ProgressReporter` abstraction.
3. `LocalRuntime` passes rich bars (current UX unchanged); the Modal entry
   points pass `None`.

## 13. Verification

```bash
# Local training (unchanged; also passes with the modal extra NOT installed)
citef train -s smoke --no-gpu --subsample 512

# Modal training (spawns, prints run id + FunctionCall id)
citef --experiment graph_embed_class train -s smoke --subsample 512 --runtime modal

# Optional pre-staging of a local dataset onto the staged volume
citef --experiment graph_embed_class train -s smoke --runtime modal \
    --stage-dataset 1920-2000-lowercase-2-embedded

# Modal evaluation
citef eval -id <run_id> -e <epoch> -s 1990-01-01 -i 1 --dry-run --runtime modal

# Cross-runtime resume, both directions (P3)
citef train -s resume --load-id <modal-run-id> --load-epoch <n>
citef train -s resume --load-id <local-run-id> --load-epoch <n> --runtime modal
```

Expected:

- Local runs work with no Modal credentials **and no `modal` package**;
  `--runtime modal` without the extra fails with the plan-1.2 §9.4 message.
- Modal train spawns; checkpoints appear as MLflow artifacts on the
  client-created run; metrics stream into the same run from the container.
- Modal eval logs metrics and `exports/<year>` artifacts to the eval run.
- Cross-runtime resume works in both directions via MLflow artifacts only.
- A missing staged dataset on the volume fails fast inside the container with
  the resolved path named.
- No runtime-specific branches in `train.py`/`eval.py`; the experiment file is
  byte-identical between venues.
- `--experiment` stays a **root-level** flag: `citef --experiment X train ...`
  (earlier drafts of this section had the flag order wrong).

## 14. Breaking changes and migration notes

Because this is v2.0, minor breaking changes are acceptable if they simplify
Modal support:

- `config/config.toml` gains `[runtime]` / `[runtime.modal]` sections; provide
  a migration note. Defaults keep local-only users untouched.
- Progress-bar construction moves from the apps into the local runtime wrapper
  (internal; no CLI change).
- `Engine` progress becomes optional (internal; §11).
- The experiment contract change (`build(runtime, env)`) landed in plan 1.1 §8
  and is a **prerequisite**, not a 2.0 break.
- Explicitly **rejected** (do not implement):
  - A `runtime` field on `RunContext` so experiments can adapt behaviour —
    invites experiment branching on the venue, violating P1/notes.md.
    Behaviour differences (e.g. `torch.compile` under snapshots) are dispatch
    decisions (§10.1).
  - Logging checkpoint *paths* to MLflow instead of artifacts — breaks P3
    cross-runtime resume.

Local-only users should not need to change any commands.
