# Plan 2.0 — Implementation steps

> Companion to `plans/2.0.md`. That document says *what* v2.0 is; this one
> sequences the work into steps that each fit comfortably in a single agent
> context window. Each step lists exact files, the changes, verification
> commands, and what must already be true before it starts.
>
> Steps are ordered so that every intermediate state is a working tree:
> local behaviour never breaks, and Modal support appears only at the end.
> Steps 1–4 are local refactors with no Modal dependency. Steps 5–8 wire up
> Modal. Step 9 ships.
>
> **Deviation from plans/2.0.md to note up front:** the experiment contract in
> the tree is `build(runtime, env, source_backend)` because plan 1.1 §8 landed
> differently than drafted. Step 1 resolves this instead of assuming it away.
> The target contract stays `build(runtime, env)`; `source_backend` CLI flags
> on train/eval are dropped (they were already meaningless for Modal), and
> experiments resolve their dataset location from `env.source`.

---

## Step 1 — Experiment portability: drop `source_backend` from the contract

**Goal:** every experiment module builds from `(runtime, env)` alone. Dataset
*identity* (name) stays in the file; dataset *location* comes from
`env.source["local"]["base_dir"]`.

**Why first:** steps 2–5 all depend on it. It is also the only step with real
semantic risk, so it gets its own window.

**Files:**

- `src/config/loader.py` — both `load_experiment` and
  `load_experiment_from_path` stop accepting/passing `source_backend`.
- `src/config/experiments/graph_embed_class.py`,
  `transformer_class.py` — change signature to `build(runtime, env)`;
  construct the source backend inline from `env.source`
  (a small helper in `data/sources` is fine, e.g.
  `build_source_from_env(env)` returning the default local backend).
- `src/apps/train.py`, `src/apps/eval.py` — delete the
  `source_backend/source_opts/source_base_dir/source_volume` options and the
  `build_source_backend_from_cli` call. Keep everything else working exactly
  as today.
- `src/apps/source_args.py` — keep for now if preprocess/describe/engineer
  still use it; check before deleting.
- `tests/test_source_args.py`, `tests/test_env_source.py` — update or remove
  tests that exercise the removed path.

**Verification:**

```bash
citef --experiment graph_embed_class train -s smoke --subsample 512 --no-gpu -e 1
citef eval -id <recent-run> -e <epoch> -s 1990-01-01 -i 1 --dry-run --no-gpu
uv run pytest
```

**Done when:** grep finds no `source_backend` parameter in `config/loader.py`
or either app; both commands pass unchanged.

## Step 2 — Engine headless mode + tracker report without rich

**Goal:** the whole train/eval loop can run with no TTY. This is plan §11,
extended to cover `tracker.report`, which the original plan missed: it takes a
`progress_bar` positionally and prints through `progress_bar.console`.

**Files:**

- `src/training/engine.py`:
  - `ProgressBars = tuple[Progress, Progress, Progress] | None`.
  - Constructor accepts `progress=None`; guard the three `add_task` calls.
  - Guard every `reset` / `advance` behind `if self._progress is not None`.
    A tiny private `_advance(idx, total=..., advance=...)` helper keeps this
    to four call sites.
  - `fit` passes `self._progress[0] if self._progress else None` to
    `tracker.report`.
- `src/training/tracking/metric_tracker.py` (and any tracker overriding
  `report`): accept `progress_bar: object | None`; when None, skip the table
  render and return metrics only.
- `src/apps/train.py`, `src/apps/eval.py`: no change yet (still pass bars).

**Verification:**

```bash
citef --experiment graph_embed_class train -s smoke --subsample 512 --no-gpu -e 1
uv run pytest tests/test_tracker_arity.py
```

Plus a quick REPL check that
`run_train_pipeline`-style headless construction works: build an `Engine` with
`progress=None` in a Python session over a small experiment and call
`eval_epoch`.

**Done when:** `Engine(experiment=..., runtime=..., progress=None)` runs
`fit(start_epoch=1, run_id="x")` end to end locally with zero rich output and
identical MLflow metrics to a progress-bar run.

## Step 3 — TrainJob / EvalJob / RunResult + `src/training/pipeline/`

**Goal:** pure functions that contain today's train and eval logic, taking a
frozen job dataclass. No runtime dispatch yet; nothing calls them except a new
test.

**Files (new package):**

- `src/training/pipeline/__init__.py` — re-export jobs and runners.
- `src/training/pipeline/_common.py` — shared helpers:
  - `write_experiment_source(source: bytes) -> Path` (tempfile, cleanup hook)
  - `build_run_context(job_env_free_fields...)` mirroring the device logic in
    `apps/train.py` (cuda-if-available).
- `src/training/pipeline/train.py`:

  ```python
  @dataclass(frozen=True, kw_only=True)
  class TrainJob:
      experiment_name: str
      experiment_source: bytes
      run_name: str
      parent_id: str | None
      start_epoch: int | None
      compile_mode: str
      fullgraph: bool
      load_id: str
      load_epoch: int | None
      model_only: bool
      subsample: int | None
      env: Env
      run_id: str = ""          # filled by the runtime wrapper via replace()
  ```

  `run_train_pipeline(job, progress=None) -> RunResult` lifts the body of
  `apps/train.py::main` after argument parsing: load experiment from bytes,
  optional compile, resume logic, params/artifact logging (the
  `save_experiment_file` + `_model_source_file` helpers move here),
  `mlflow.start_run(run_id=job.run_id)`, `engine.fit`. Returns final metrics
  in `RunResult.metrics`.

- `src/training/pipeline/eval.py`: `EvalJob` per plan §9.1 (drop
  `prefix`-into-path logic; exports become MLflow artifacts under
  `exports/<year>` written from a temp dir — see deviation note below).
  `run_eval_pipeline(job)` lifts the sliding-window loop verbatim, including
  the `GraphDataset.with_window` / DataLoader rebuild, but writes predictions
  to `tempdir/<year>` and calls `mlflow.log_artifacts(dir,
  artifact_path=f"exports/{year}")` instead of `tracker.export_loc` under the
  staged dir. Keep `clean_up`.

  **Deviation:** today's eval deletes and recreates
  `<base_dir>/eval/<run_id>/run-<prefix>` and points `tracker.export_loc`
  there. Pipelines write to a temp dir and export through MLflow artifacts on
  both venues (plan P3 logic applied to predictions). The `--temp-dir` /
  `--clean-up` flags keep their meaning.

- `RunResult` lives in `src/runtime/base.py` per plan §6 so both runtimes and
  pipelines can reference it without a circular import (pipelines import from
  `runtime.base`; `runtime.base` imports nothing from training).

- New test `tests/test_pipeline_jobs.py`: frozen-dataclass round-trip +
  `run_eval_pipeline` failing fast ("No experiment file found") when the run
  id is bogus. Full behavioural coverage comes from the smoke runs in later
  steps; do not chase mock-heavy unit tests here.

**Verification:**

```bash
uv run pytest tests/test_pipeline_jobs.py
```

Tree still behaves as before: apps untouched in this step.

**Done when:** both pipelines import cleanly, the fail-fast test passes, and
`grep -rn "if runtime == " src/apps` is empty (it already should be).

## Step 4 — Rewire apps onto the pipelines (local-only)

**Goal:** `train.py` / `eval.py` shrink to parse → build job → delegate. This
step introduces `Runtime.run_train` / `run_eval` on the protocol and implements
them only on `LocalRuntime`, which calls `run_train_pipeline` in-process.

**Files:**

- `src/runtime/base.py` — add `run_train(self, job: TrainJob) -> RunResult`
  and `run_eval(...)` to the protocol.
- `src/runtime/local.py` — implement both: perform the client-side run
  lifecycle (plan §8.3: read `experiment_name` from the module without calling
  build — import via the same `_load_module_from_path` helper, moved or
  re-exported from `config.loader`; set tracking uri/experiment;
  `MlflowClient().create_run(...)` with `run_name`/`parent_id`; log params +
  experiment/model source artifacts; `dataclasses.replace(job,
  run_id=run.info.run_id)`), then call the pipeline with
  `progress=build_progress_bars(disable=not job.progress_flag)` — carry a
  `progress: bool` field on `TrainJob` for this, or pass bars from the app;
  pick one and document it. Return the completed result.
- `src/runtime/modal_runtime.py` — add stub methods raising
  `NotImplementedError("Modal training lands in step 6")` so the protocol is
  satisfied.
- `src/apps/train.py` — keeps every existing flag, adds nothing yet. Builds
  `TrainJob` (reads the experiment file bytes itself), calls
  `runtime.run_train`, logs the result. Deletes: engine setup, mlflow
  start_run block, resume block, checkpoint helpers.
- `src/apps/eval.py` — same treatment. Drops the `--gpu` assert path into the
  job; drops the LocalSourceBackend requirement entirely (that was only for
  prediction output, which is now MLflow artifacts).

**Verification:** identical commands to step 1, plus cross-resume:

```bash
citef --experiment graph_embed_class train -s smoke --subsample 512 --no-gpu -e 1
citef train -s resume-smoke --load-id <id> --load-epoch 1 --no-gpu -e 1
citef eval -id <id> -e 1 -s 1990-01-01 -i 1 --dry-run --no-gpu
# then confirm exports/<year> artifacts appear on the eval run in the MLflow UI
```

**Done when:** both apps contain no `mlflow.start_run`, no `Engine`, no
checkpoint imports; all three commands behave as before (modulo eval exports
now landing as artifacts).

This is the biggest step. If it strains the window, split 4a (protocol +
LocalRuntime.run_train + train.py) from 4b (eval mirror); they share no code
paths once step 3 is done.

## Step 6 — Modal training GPU class + `ModalRuntime.run_train/run_eval`

**Goal:** the actual cloud execution. Depends on steps 1–5.

**Files:**

- `src/runtime/modal_runtime.py`:
  - `train_image` per plan §10.3 (debian_slim 3.13, pip from pyproject,
    `add_local_dir("src", "/root/src")`, PYTHONPATH). Mirror the image style
    already used for the embedding class at the top of this file.
  - `@modal.cls` `ModalTrainingGPU` per plan §10.1: mounts staged +
    checkpoint volumes, `gpu=train_gpu`, long timeout,
    memory/gpu snapshot flags following `production/service.py` precedent,
    `.train()` / `.eval()` methods calling the pipelines with `progress=None`.
    Snapshot caveat: when snapshotting is enabled the dispatcher forces
    `job.compile_mode = ""`.
  - `ModalRuntime.run_train`:
    1. Reject loopback `env.tracking_uri` client-side with a clear message
       unless `[runtime.modal].tracking_uri` overrides it (§10.5).
    2. Derive container Env: `replace(env, tracking_uri=<override or same>,
       artifact_loc=Path(f"/modal/{checkpoint_volume}"),
       source={...base_dir=f"/modal/{staged_volume}"})` — note this goes
       through `env.source`, not invented `raw_loc` fields, because step 1
       made `env.source` the location channel.
    3. Client-side run lifecycle (same helper as LocalRuntime — extract it
       into `src/runtime/run_lifecycle.py` during this step so both runtimes
       share one implementation).
    4. `.spawn()` the remote method; print run id + FunctionCall id; return
       `RunResult(status="spawned", ..., modal_function_call_id=...)`.
  - `ModalRuntime.run_eval`: same shape, blocking `.remote()` acceptable for
    eval if spawn complicates the first pass; record the choice.
- `src/runtime/factory.py` — pass the full modal config through (it already
  reads `env.runtime.get("modal", {})`; extend what it forwards).

**Verification (needs Modal credentials):**

```bash
citef preprocess --runtime modal            # ensure staged volume populated
citef --experiment graph_embed_class train -s smoke --runtime modal \
    --stage-dataset <staged-name>           # optional convenience flag, add here
modal FunctionCall.from_id(<id>).get()      # block and inspect logs
```

Then confirm checkpoints appear as artifacts on the client-created run and
metrics streamed in from the container.

**Done when:** a spawned smoke train completes on Modal with artifacts on the
expected run, and `--runtime modal` without the extra installed still fails
with the existing friendly message.

## Sizing notes

| Step | Risk | Why it fits one window |
|------|------|------------------------|
| 1 | Medium — touches both experiments and both apps | Mechanical signature change, two experiment files |
| 2 | Low | One class + one method family |
| 3 | Low-medium | Mostly lifting existing code into new modules |
| 4 | Highest | Two app rewrites; split into 4a/4b if needed |
| 5 | Trivial | Config + one accessor |
| 6 | Medium | One file grows, but patterns exist in-file already |
| 7 | Unknown | Reserved slack for integration findings |
| 8–9 | Low | Mechanical |

Step 3 and step 5 are independent if parallelising across sessions.
