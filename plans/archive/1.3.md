# Plan 1.3 — Modal runtime for describe and engineer

> **Scope:** extend the Modal runtime introduced in plan 1.2 to the remaining
> data-pipeline apps (`describe` and `engineer`). After this plan, the full
> data pipeline — preprocess, describe, engineer — can run on either local
> filesystems or Modal volumes with a single `--runtime modal` flag.
>
> This is the third step of the runtime unfold. It stays in the v1.x line
> because it is still additive: no experiment-training logic changes yet.

---

## 1. Goal

`citef describe` and `citef engineer` support `--runtime modal`:

- **local** (default): reads/writes local paths via `LocalStagedSource`.
- **modal**: reads/writes Modal volumes, runs the whole job inside a Modal
  container.

App logic in `src/apps/describe.py` and `src/apps/engineer.py` does not branch
on the runtime string; it delegates to `runtime.run_describe(...)` and
`runtime.run_engineer(...)`.

---

## 2. Principles

| # | Principle |
|---|---|
| P1 | **One app, two runtimes.** No `if runtime == "modal"` in app files. |
| P2 | **Whole-job remote execution.** Describe and engineer run as complete Modal jobs, not piecemeal RPCs. |
| P3 | **Reuse the 1.2 runtime.** Volume labels, image, and GPU config come from the same `[runtime.modal]` section. |
| P4 | **Local-first safety.** Local smoke tests must still pass without Modal credentials. |

## 4. Runtime protocol additions

Extend the `Runtime` protocol from plan 1.2:

```python
class Runtime(Protocol):
    def get_source(self, root: str | Path, name: str) -> DataSource: ...
    def get_embedder(self, key: str, **kwargs: Any) -> TextEmbedder: ...
    def maybe_download(self, source: DataSource) -> Path: ...
    def maybe_upload(self, source: DataSource, local_path: Path) -> None: ...
    def run_preprocess(self, job: PreprocessJob) -> DataSource: ...
    def run_describe(self, job: DescribeJob) -> None: ...
    def run_engineer(self, job: EngineerJob) -> DataSource: ...
```

- `run_describe` returns `None` because it only logs/prints descriptives.
- `run_engineer` returns the output `DataSource`.
- `LocalRuntime` implements all three by calling the pipeline functions
  in-process.
- `ModalRuntime` implements all three by dispatching to Modal functions.

## 7. Modal runtime additions

### 7.1 `src/runtime/modal.py`

Add two Modal functions that mirror the preprocess pattern:

```python
@app.function(
    volumes={
        "/modal/<raw-volume>": raw_volume,
        "/modal/<staged-volume>": staged_volume,
    },
    image=preprocess_image,
)
def run_describe_remote(job: DescribeJob) -> None:
    local_runtime = _in_container_runtime()
    run_describe_pipeline(job)


@app.function(
    volumes={
        "/modal/<raw-volume>": raw_volume,
        "/modal/<staged-volume>": staged_volume,
    },
    image=preprocess_image,
)
def run_engineer_remote(job: EngineerJob) -> DataSource:
    local_runtime = _in_container_runtime()
    return run_engineer_pipeline(job)
```

- Both functions mount the staged volume (and raw volume if needed).
- They build a lightweight in-container runtime and call the same pipeline
  functions used locally.
- `_in_container_runtime()` is a small shared helper defined in
  `src/runtime/modal.py` returning a `LocalRuntime` bound to the in-container
  volume mount roots; the 1.2 preprocess function uses the same helper.
- Volume labels and image come from the shared `[runtime.modal]` section (P3),
  and `[runtime].default` is honoured by these apps exactly as in 1.2 — the
  `--runtime` flag is only a per-invocation override.

### 7.2 No GPU required

Describe does not need a GPU. Engineer’s DBSCAN is CPU-bound; keep it on a
standard Modal container for 1.3. If profiling shows DBSCAN is a bottleneck, a
future optimisation can add a GPU-accelerated DBSCAN variant without changing
the app code.

## 8. Verification

```bash
# Local smoke tests
citef describe -d <dataset> --staged-loc /tmp/data
citef engineer -d <dataset> -o <output> --staged-loc /tmp/data

# Modal smoke tests
citef describe -d <dataset> --runtime modal
citef engineer -d <dataset> -o <output> --runtime modal
```

Expected:

- Local runs do not require Modal credentials.
- Modal runs read from and write to the configured Modal volumes.
- Output schemas are identical between local and Modal runs.
- `metadata.json` for engineer records `runtime: modal`.

---

## 9. Versioning

**Stay in v1.3.** This release completes the Modal data pipeline but does not
yet touch the training/evaluation loop. It is additive and backward-compatible
for local users.

The boundary for v2.0 is intentionally reserved for `train`/`eval` on Modal
(see plan 2.0), because that changes the core experiment loop and production
architecture.

Deviations from this document:

- `maybe_download` / `maybe_upload` were not added to the `Runtime` protocol;
  no caller materialised and preprocess already runs without them.
- Engineer gained a `runtime_name` field and writes `metadata.json`
  (`runtime`, job parameters) to satisfy §8; preprocess already did this.
- Fixed pre-existing bug found by the §8 smoke command:
  `--input-path` defaulted to `""`, which typer converts to truthy `Path(".")`,
  so `-d <dataset>` without `-i` used the CWD as origin. Now defaults to `None`.
- The Modal app was renamed `citef-preprocess` → `citef-data`; all functions
  deploy together so `modal.Function.from_name` lookups stay consistent.
- Remote container logs are not streamed to the local console; success is the
  returned result / exit code, and exceptions propagate back.

Verification (2026-08-24): deployed `citef-data`; ran describe/engineer locally
and via `--runtime modal` against `all-lowercase-2-subset` (789k rows,
2 partitions). Local vs modal outputs have identical schemas and row counts;
volume `metadata.json` records `runtime: modal`. Temp dataset
`tmp-13-llc2-engineered` remains on the `openalex-staged` volume
(`modal volume delete` cannot remove prefixes in CLI 1.5.4).
