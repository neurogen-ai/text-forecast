# Plan 2.4 — Modal runtime tidy-up

> **Scope:** remove the over-engineering and duplication introduced by the
> agent-written 2.0 runtime branches while changing no behaviour that matters.
> Inline pointless wrappers, cut noise logging down to dispatch boundaries,
> single-source the volume labels and the `<experiment>-EVAL` naming, and
> move remaining `assert`-based input validation to explicit raises.
>
> **Prerequisites:** plan 2.1. The clean-pipeline refactor is out of scope
> here, but the two plans touch the same files (`apps/preprocess.py`,
> `data/preprocess/pipeline.py`) and overlap on the "no asserts" rule, so
> land 2.1 first to avoid duplicate edits.
>
> **Out of scope:** production deployment hardening (plan 2.5), distributed
> GPU training (plan 2.6), remote progress tracking (plan 2.7). None of the
> changes below alter the experiment contract, the CLI surface, or the job
> serialisation format.

---

## 1. Problems being fixed

### 1.1 Padded, trivial logging

`runtime/modal_runtime.py` makes 32 logger calls. Many log the obviously
expected (method entry/exit are each logged separately: "starting train job"
then the pipeline logs it again). This reads as observability padding rather
than useful signal and buries the real dispatch/error lines.

### 1.2 Pointless indirection

- `_in_container_runtime()` is a function whose body is only
  `return _InContainerRuntime()`.
- `_key_to_model_name()` and `_embedder_config()` are one-call wrappers.

Each adds a name to learn without adding meaning.

### 1.3 Volume label duplicated across config and a module constant

`modal_runtime.py` hardcodes `VOLUME_LABEL = "openalex-staged"` and other
volume constants, while the same values live in `[runtime.modal]` in
`config.toml`. `ModalRuntime.__init__` then raises at runtime if the two
disagree. Two sources of truth plus a "keep them in sync" error is worse than
one source. `config/env.py` already reads these into `ModalRuntimeConfig`
(`staged_volume`, `checkpoint_volume`, `raw_volume`); the constants should be
deleted and the config value used everywhere.

### 1.4 EVAL experiment naming computed twice

> **Correction:** the fallback is computed in **three** places, not two:
> both runtimes (`ModalRuntime.run_eval`, `LocalRuntime.run_eval`) plus
> `run_eval_pipeline`; see deviation 1 in `plans/implementation/v2.4.md`.

Both `ModalRuntime.run_eval` (lines ~415) and `run_eval_pipeline`
(`eval.py` ~98) independently derive:

```python
mlflow_experiment = job.experiment_name or f"{training_experiment}-EVAL"
```

Two copies that can drift silently. One owner should compute it; the other
should read the result.

### 1.5 `assert` used for input validation

`apps/preprocess.py`, `_common.build_run_context`, and `eval._validate` guard
user input with `assert`, which is stripped under `python -O`. Input
validation must raise explicitly.

### 1.6 Import-time side effects

`runtime/modal_runtime.py` calls `load_env()` at module import (partly
justified: Modal decorators need config at import). `apps/preprocess.py` sets
`os.environ["TOKENIZERS_PARALLELISM"]` at import. `pipeline.py` sets
`POLARS_MAX_THREADS` inside `run_preprocess_pipeline` — polars reads that
env var once at its own import, so setting it here almost certainly does
nothing; `max_threads` may be dead.

## 2. Design

### 2.1 Cut logging to dispatch boundaries

In `modal_runtime.py`, keep one INFO line per public `run_*`/remote method
(entry with the job id / run id), one on completion or failure. Drop the
per-step debug noise ("starting X" / "finished X" pairs) and the `_build_modal_embedder`
trace. Keep the config dump at DEBUG behind a single line. Target: under 12
logger calls, each carrying state a reader can't recover from return values.

### 2.2 Inline the wrappers

- Replace `_in_container_runtime()` usage with `_InContainerRuntime()` at the
  call site.
- Fold `_embedder_config` / `_key_to_model_name` into `_build_modal_embedder`.
  Delete the now-unused helpers.

### 2.3 Single source for volume labels

`modal_runtime.py` should import `modal_runtime_config(env)` and read volume
labels from `[runtime.modal]` through `ModalRuntimeConfig`, not module
constants. Delete `VOLUME_LABEL`, and if nothing else references it, the
`ModalRuntime.__init__` mismatch check goes with it. The `app.cls` /
`app.function` decorators run at import, so the config must still be loaded
at module import; the point is the config is the only place the label is
spelled. Keep `EMBEDDERS_MOUNT` (`/embedders`) as a mount path, it's a path
not a config key.

### 2.4 One owner for EVAL naming

Put `mlflow_experiment` derivation in `run_eval_pipeline` (it already needs
it for local dispatch and logging artifacts). In `ModalRuntime.run_eval`,
stop recomputing the `-EVAL` fallback: compute only the pieces the client
needs up front (`training_experiment`, and the eval run id), and either rely
on the pipeline for the final experiment name or pass the derived name
through the job. Prefer: client owns nothing about the fallback name; the
pipeline owns it; `EvalJob` carries an optional explicit override as today.

If the pipeline needs the experiment name before the run is created
(create_run precedes dispatch), compute it in one shared helper
`eval_experiment_name(job)` in `training/pipeline/eval.py` and call that from
both the client wrapper and the pipeline body. That keeps a single
implementation with two call sites.

> **Correction:** as noted in §1.4 there are three call sites (both runtime
> clients plus `run_eval_pipeline`); branch C of
> `plans/implementation/v2.4.md` single-sources all three.

### 2.5 Explicit raises, then delete asserts

Move the input guards in `apps/preprocess.py`, `_common.build_run_context`,
and `eval._validate` to `raise ValueError` (or `typer.BadParameter` in the CLI
layer). Delete the asserts afterward. Add no new behaviour; keep the exact
message text so tests that match on them still pass.

### 2.6 Env-var tidying

- `pipeline.py`: with 2.1 landed, confirm whether `POLARS_MAX_THREADS` post-import
  has any effect. If not, drop the line and the `max_threads` job field, or
  move it to process entry (the preprocess app already has import-time env).
- `apps/preprocess.py`: keep `TOKENIZERS_PARALLELISM` (torch tokenizers need
  it before use) but note it in a comment; it is justified.

Import-time `load_env()` stays; removing it would break Modal decorators and
is out of scope.

## 3. Tasks

Each task lands as one commit, sized for a single session.

### T0 — Logging cut | `runtime/modal_runtime.py`

Reduce to one INFO line per public dispatch method and one per remote entry
point. Delete the `_build_modal_embedder` trace and the entry/exit debug
pairs. Keep one DEBUG config summary. No logic change. Verify the CLI docs
`docs/apps.md` still describe Modal dispatch correctly.

### T1 — Inline wrappers | `runtime/modal_runtime.py`

Replace `_in_container_runtime()` call site with `_InContainerRuntime()`.
Fold `_embedder_config` / `_key_to_model_name` / `_resolve_output_dim` as
cleanly as possible into `_build_modal_embedder`; keep `_resolve_output_dim`
if it stays distinct and used. Delete dead helpers.

### T2 — Volume labels single source | `runtime/modal_runtime.py`, `config/env.py`

Read `staged_volume` / `checkpoint_volume` / `raw_volume` from
`ModalRuntimeConfig` for the `app.cls` / `app.function` decorators and the
`ModalRuntime` methods. Delete `VOLUME_LABEL` and any now-orphaned constants.
Delete the `ModalRuntime.__init__` mismatch check if nothing else needs the
constant. Keep `EMBEDDERS_MOUNT`. Update `test_modal_config.py` /
`test_modal_env.py` if they referenced the constants.

### T3 — Single EVAL naming | `training/pipeline/eval.py`, `runtime/modal_runtime.py`

Add `eval_experiment_name(job)` helper in `eval.py` implementing the
fallback (`job.experiment_name or ...`). Call it from both `run_eval_pipeline`
and `ModalRuntime.run_eval`. Confirm the `-EVAL` and `eval-{run_id}` cases
produce identical experiment names as before. Add a focused unit test for the
helper.

### T4 — Asserts to raises | `apps/preprocess.py`, `training/pipeline/_common.py`, `training/pipeline/eval.py`

Convert the input-validation asserts to `raise ValueError` / `raise typer.BadParameter`.
Delete the asserts. Mirror the exact current messages. Run the existing
validation tests; add one that asserts a `ValueError` (not `AssertionError`)
surfaces.

### T5 — Env-var check | `data/preprocess/pipeline.py`

Investigate the `POLARS_MAX_THREADS` post-import question (2.1's Dispatch
step will print polars thread counts, or a quick REPL under the project pin
settles it). Remove the line and `max_threads` if dead, or move it to app
entry if live. Document the conclusion in the commit. This task is the only
one with an open behavioural question; do it last so 2.1's rewiring is in.

## 4. Risks

- **Volume-label change breaks config users.** If `config.example.toml` or
  running installs spell a volume label that differs from the old constant,
  T2 changes which volume is mounted. Grep `config/` and docs for every label
  string before deleting constants, and keep `config.example.toml` in sync.
- **EVAL rename drift.** If the helper in T3 returns a different string than
  the old inline code, eval runs land in a new experiment. Lock the mapping
  with the T3 unit test first, then swap call sites.
- **Assert removal is mechanical but visible.** Double-check no test depends
  on `pytest.raises(AssertionError)`; the `_validate` path is the likely spot.
- **Logging cut can hide a useful line.** If a debug line is the only place a
  failure reason is logged, keep it or move it to the error path rather than
  deleting. Re-check against the CI/test output for runtime.

Old-behaviour mapping and context are preserved in `docs/apps.md` and
`docs/training.md`; if either documents the number of Modal logger calls or
the volume-constant contract, update it.
