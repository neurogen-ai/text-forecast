# Plan 2.4 — Production deployment hardening

> **Scope:** harden the Modal runtime from plan 2.0 into a production-grade
> deployment: CI/CD for Modal images, secrets management, monitoring/retry
> logic for long-running jobs, scheduled retraining, and incremental dataset
> updates.
>
> **Prerequisites:** plan 2.3 merged first. Implementation branches B/C/E of
> `plans/implementation/v2.4.md` edit `src/runtime/modal_runtime.py` using
> post-2.3 naming (e.g. `_STAGED_VOLUME_LABEL`), so those branches must not
> start against pre-2.3 code.
>
> This is a v2.x release because it builds on the v2.0 hybrid local/cloud
> foundation without changing the core training architecture.

---

## 1. Goal

Citation-forecast can be operated as a production system:

- Modal images are built and published automatically.
- Sensitive configuration lives in Modal secrets, not in `config.toml`.
- Long-running training jobs are monitored and retried on failure.
- Datasets can be updated incrementally without reprocessing everything.
- Optional web endpoints and scheduled functions support retraining and
  inference pipelines.

---

## 2. Principles

| # | Principle |
|---|---|
| P1 | **Secure by default.** No secrets in repo or `config.toml`. |
| P2 | **Automated pipelines.** Image builds and smoke tests run in CI. |
| P3 | **Observable.** Jobs emit structured logs and metrics; failures are retried. |
| P4 | **Incremental.** Dataset updates reuse existing staged data where possible. |
| P5 | **Optional web surface.** Scheduled jobs and endpoints are opt-in. |

## 4. CI/CD for Modal images

### 4.1 GitHub Actions workflow

- Build `preprocess_image` and `train_image` on every PR and publish on tags.
- Use Modal’s CLI or a custom script to push images to the Modal registry.
- Fail the build if `basedpyright` strict fails on Modal runtime paths.

### 4.2 Image versioning

- Tag images with the git tag or short SHA.
- `config.toml` can reference a specific image tag for reproducibility.

---

## 5. Secrets management

- Store Modal tokens, MLflow tracking credentials, and any cloud provider keys
  as Modal secrets.
- `src/runtime/modal.py` reads secret values via `modal.Secret.from_name(...)`
  and injects them into the container environment.
- Remove plaintext credentials from `config.toml`. Example:

```toml
[runtime.modal]
secrets = ["cf-modal-token", "cf-mlflow-creds"]
```

## 6. Monitoring and retry logic

### 6.1 Job wrapper

Add a `MonitoredModalJob` wrapper around `ModalRuntime.run_*` methods:

- Log job start/end/failure with run IDs.
- Poll `modal.FunctionCall.from_id(...)` for the jobs plan 2.0 §10.2 spawns —
  `RunResult.modal_function_call_id` is the join key. Because the 2.0 CLI
  returns immediately (fire-and-forget), this wrapper is the only local
  visibility channel until plan 2.6 lands.
- Capture Modal function logs and surface them locally.
- Retry transient failures (up to a configurable limit).
- Report final status via exit codes.

> **Correction:** the `MonitoredModalJob` wrapper class was replaced by free
> functions (`status_from_call`, `spawn_with_retry`, `wait_for_call` in
> `src/runtime/monitoring.py`) plus a `citef status` command; see
> `plans/implementation/v2.4.md`.

### 6.2 Health checks

- For long training runs, periodically heartbeat to MLflow or a lightweight
  status endpoint.
- Detect hung jobs and surface them to the operator.

## 7. Incremental dataset updates

### 7.1 Versioned Modal volumes

- Support dataset versions in `ModalVolumeSource`:

```python
@dataclass(frozen=True, kw_only=True)
class ModalVolumeSource:
    volume_label: str
    path: str
    name: str
    version: str | None = None
```

- `resolve()` returns `/modal/<volume>/<path>/<name>/<version>`.

> **Correction:** the `ModalVolumeSource` dataclass was dropped in favour of
> extending the existing `ModalDataSource` with an optional `version` field;
> see `plans/implementation/v2.4.md`.

### 7.2 Incremental preprocessing

- Add an `--incremental` flag to `citef preprocess`.
- When enabled, the pipeline reads the previous staged version, identifies new
  raw partitions, and only processes the delta.
- Write the result to a new versioned destination.

## 10. Versioning

**Stay in v2.4.** This release hardens the v2.0 foundation without changing the
core experiment or training architecture. It is a natural v2.x follow-up.

Two further v2.x releases are already planned and should **not** be absorbed
into this plan:

- **`plans/releases/2.5.md` — distributed GPU training/eval.** The train/eval
  pipelines from 2.0 must be refactored for multi-GPU execution (DDP-style
  sharding, rank-aware tracking/checkpointing).
- **`plans/releases/2.6.md` — remote progress tracking.** Replaces the headless
  `progress=None` mode from 2.0 §11 with a live reporting channel (MLflow
  metrics first, per the owner's preference).

Future major-version bumps (v3.0) would require a larger architectural shift,
such as a new serving platform, a redesign of the experiment format, or
multi-node distributed training clusters (the distributed-training plan,
2.5, covers single-node multi-GPU only).
