## Scope checklist

- Feed `train_ids` from `training_step`, matching the id tracking the validation path already has.
- The empty-store message in `_gather_store` becomes a latched one-time WARNING per store name.
- `run_eval_pipeline` sets the tracking URI before starting the MLflow run.
- Bare `logger.error(e)` in the tracking package becomes `logger.exception` with a context string.
- Log the full hyperparameter set to the train run at start, keyed by readable leaf names with explicit suffix disambiguation on ambiguity.
- Delete the dead `log_params` helper and `_get_scheduler_params`.

## Technical approach and risk

### Architecture choices

- The id fix feeds the store. The gather is never deleted or made conditional at the call site; the validation path feeds ids today and five tracker subclasses share the same store names, so both rejected fixes silence the symptom while leaving the train/val id asymmetry in place.
- The feed skips only NaN-fallback id batches. `TokenBatch.id` is typed non-optional and `return_id=False` configs emit a NaN fallback, so an unguarded feed would trade the empty-store ERROR spam for NaN-rejection ERROR spam. The NaN-rejection message level gets reviewed in the same pass, because a fully-NaN id batch is a config fact, not an error.
- The latched WARNING follows the `VectorRetriever._warned_no_candidates` pattern in src/models/retrieval_forecast.py: one plain line per store name, no counters. Pure DEBUG would bury the "eval window matched zero rows" case this message exists for.
- The tracking-URI fix is a two-line reorder, no API change. Threading an explicit MLflow client through the pipeline belongs to a larger tracking refactor.
- The `logger.exception` swaps stay inside the tracking package.
- Params are logged from the materialized Experiment and RunContext in the train pipeline, the one place every resolved value already exists. A generic scalar walker recurses into dataclasses and pydantic models, keeps str/int/float/bool, and stringifies other objects as class names.
- Param keys are bare leaf names by default (lr, epochs, embed_dim). Ambiguous leaves are disambiguated leaf-first: `embed_dim-embedder`, `embed_dim-forecaster`, `batch_size-train`, `batch_size-val`. Ambiguous leaves log both the bare key and all suffixed keys on every run, so the key set is identical across runs. The disambiguation lives in an explicit rename table in its own module, separate from the walker; renaming or adding a key is a one-place edit.
- Model hyperparameters are captured by convention: 20 of the 21 model families keep their constructor config as `self.config` and get flattened; `graph_recurrent` stores hyperparams as plain attributes and rides as class-name-only until it gains a config dataclass.
- MLflow params are immutable per run and the train pipeline reuses `job.run_id` on resume, so the param log is guarded: identical values are a no-op, changed values warn instead of raising. A mismatch on resume means the operator should have taken a new run_id, which the parent CLI flags already provide.
- Eval keeps its `eval.*` params untouched. Params only, no tags.

### Friction points

All MINOR.

- Feeding `train_ids` grows the gathered train store by one int64 per example (14,853 per epoch at current shapes). Absorbed by existing buffers.
- With export enabled, `train_ids.npy` joins the debug export payload; consumers of the exported arrays gain a column. No metric names or values change, and the export format is not a documented contract. Record in the commit.
- The URI reorder changes behaviour only for processes that had a stale URI set. Those runs were writing to the wrong store and were already broken.
- MLflow caps param key and value lengths; the walker truncates stringified values rather than raising. Only exotic fields can hit this.
- On resume with a changed config, the guarded param log keeps the original run's values and warns. The original config is what produced the checkpoint, so that is arguably the correct record.
- StrategyConfig holds live objects (model, tracker, stream, device); the walker's scalar filter must skip them or run start raises.

Cost: small. Two feed lines plus a guard in classification.py, one level change in metric_tracker.py, a two-line reorder in eval.py, mechanical logger swaps, and one scalar-walker helper with its rename table and test. Smaller than Branch D of plans/implementation/v2.5.md (assert-to-raises).

### Descope triggers

- If a train config mixes real and fallback ids inside one batch, cut the feed lines and ship the latched WARNING plus the URI reorder. Check: inspect id tensors across the existing experiment configs in the first commit.
- If the `logger.exception` swaps in the plot paths produce noisy tracebacks per eval epoch, cut those swaps and keep the fix in `calc_metrics` only. Check: the first eval run's log.
- If the walker raises on any existing experiment config at run start, cut the walker and log an explicit hand-written param dict (the four current params plus the spec fields). Check: the first train run of each existing experiment config.
- If flattening a model's `self.config` fails to serialize cleanly, cut that family back to `model_class` only. Check: the first-commit model survey has been run; 20 of 21 families keep `self.config`, `graph_recurrent` is listed as class-name-only, so only a serialization failure can fire this trigger.
