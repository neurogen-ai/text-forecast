# Plan 2.2 — CLI launch speed: lazy heavy imports

> **Scope:** make `text-forecast --help` (and every arg-parse error, `--help`,
> and dispatch boundary) responsive by deferring heavy third-party imports
> (torch, transformers, mlflow, seaborn, sklearn) out of module scope and
> into the functions that actually need them. Modal client paths must never
> import torch. No CLI surface, job serialisation, experiment contract, or
> pipeline behaviour changes.
>
> **Prerequisites:** plan 2.1 (implemented). The clean-pipeline refactor is
> done; this release touches some of the same files (`apps/preprocess.py`)
> but no overlapping logic.
>
> **Out of scope:** modal runtime tidy-up (plan 2.5.0), production hardening
> (2.6), distributed training (2.7), remote progress (2.8). Polars/pandas are
> NOT deferred wholesale — see §3.

---

## 1. Problems being fixed

### 1.1 Baseline: 7.4s to reach arg parsing

`PYTHONPATH=src python -c "import main"` takes **7.44s** and loads torch,
transformers, mlflow, seaborn, sklearn, polars and pandas before typer can
parse a single argument. Every invocation pays this, including `--help`,
bad flags, and dry dispatch checks.

The chains responsible:

| Chain | Culprit |
|---|---|
| `main` → `apps/__init__` re-exports → each app module | each app top-level-imports its job/pipeline modules |
| `main` → `config.loader` → `config.experiment:5-6` | `from torch import nn`; also pulls training/checkpointing, strategies, tracking |
| `config.runtime:11` | `torch.device`/`torch.dtype` field types on `RunContext` |
| `runtime.local` / `runtime.modal_runtime` | top-level imports of `training.pipeline.{train,eval}`, `data.preprocess.*`, `run_lifecycle` (mlflow) |
| `apps.preprocess` | `data.preprocess.{pipeline,steps}` → tokenise (transformers), embed_huggingface (torch+transformers) |

### 1.2 Modal paths import torch client-side

`runtime/factory.py` already lazy-imports `modal_runtime` (the repo's canonical
pattern), but `modal_runtime.py`'s own top level imports
`training.pipeline.{train,eval}`, `embed_huggingface`, and `run_lifecycle` —
none of which the client needs: torch appears there only in comments about
`torch.compile`. A `--runtime modal` run on a machine without torch would
currently fail at import time even though execution happens remotely.

## 2. Principles

1. **Defer modules, not side effects.** The only import-time side effects in
   the tree are deliberate and must NOT move:
   - `apps/train.py:17` `warnings.filterwarnings("ignore")` — must stay
     module-level so it still silences warnings from later heavy imports;
   - `apps/preprocess.py:28` `os.environ["TOKENIZERS_PARALLELISM"] = "true"`
     — must be set before transformers loads anywhere in-process; keeping it
     at app-module level preserves that guarantee.
   Everything else deferred is pure class/function definitions with no
   import-time behaviour (verified by inventory in §6/T1).
2. **Lazy at the edge, not everywhere.** Heavy imports move to the *shallowest*
   function that needs them — command bodies in `apps/*`, method bodies in
   `runtime/*`, loader functions in `config/loader.py`. Pipeline-internal
   modules keep importing each other normally; we do not sprinkle function-
   level imports through `training/` or `data/`.
3. **One style.** Function-local imports follow the existing
   `runtime/factory.py:23-38` pattern (function-local `from .x import Y`,
   try/except ImportError only where the dependency is genuinely optional,
   explanatory comment where non-obvious). Type-only dependencies use
   `TYPE_CHECKING` guards per the existing precedent in `runtime/base.py`
   and rely on the `from __future__ import annotations` headers already
   present in every touched file.

## 3. Changes

### 3.1 `config/` — break the torch chain in the root callback

- `config/experiment.py`: move `from torch import nn`,
  `torch.utils.data.DataLoader`, `training.checkpointing`,
  `training.strategies`, `training.tracking.base` behind `TYPE_CHECKING`;
  annotations become strings (header already present). These names are used
  only as field/callable types.
- `config/runtime.py`: same treatment for `torch.device`/`torch.dtype` on
  `RunContext`.
- `config/loader.py`: drop module-level `.experiment` and `.runtime`
  imports. `load_experiment`/`load_experiment_from_path` import
  `config.experiment.Experiment` locally (they need the real class for the
  isinstance checks); `RunContext` becomes a `TYPE_CHECKING` annotation only.
  `available_experiments`, `resolve_experiment_name`, `read_experiment_name`
  (AST-based) stay exactly as-is — they never needed torch.
- **Guard:** nothing in these files may call `typing.get_type_hints` on
  `Experiment`/`RunContext` at runtime afterwards. Current audit:
  `get_type_hints` is used only in `data/preprocess/steps.py:97` over
  preprocess-step dataclasses, which do not gain stringified annotations.
  Add this invariant as a comment at both dataclasses.

### 3.2 `apps/*` — light module scope

Each app module keeps its Typer sub-app, options, callbacks, and the two
deliberate side effects listed in §2, but moves these to inside its command
functions:

- `apps/describe.py`: `data.pipeline.describe`, `runtime` imports.
- `apps/engineer.py`: `data.pipeline.engineer`, `data.sources`, `runtime`.
- `apps/eval.py` / `apps/train.py`: `runtime.factory`,
  `training.pipeline.{eval,train}`.
- `apps/preprocess.py` (+ `apps/preprocess_ops.py`):
  `data.preprocess.{pipeline,steps}`, `data.sources`, `runtime`.
- `apps/source_args.py`: `config.env`, `data.sources` (only needed when
  building overrides).

`apps/__init__.py` re-exports stay unchanged: once the app modules are light,
eagerly importing them is cheap and avoids any registration trickery in
`main.py`.

`main.py` itself needs no structural change beyond what §3.1 buys it; verify
its remaining imports (`typer`, `tomllib`, `utils.get_root_dir`) are stdlib/
light.

### 3.3 `runtime/*` — torch-free modal client, deferred local heavies

- `runtime/local.py`: move `data.pipeline.*`, `data.preprocess.embed`,
  `data.preprocess.pipeline`, `data.sources.local`, `training.pipeline.*`
  into the methods that use them. `runtime.run_lifecycle` (mlflow) is
  likewise imported inside `create_run` callers — mlflow stays module-level
  *in* `run_lifecycle.py` itself; deferring the import of the module is
  enough and keeps one mlflow-import site.
- `runtime/modal_runtime.py`: keep `modal`, `config.env`, `config.loader`
  (AST reader — light) at module level; move `DescribeJob`/`EngineerJob`/
  `PreprocessJob`/`EvalJob`/`TrainJob` + pipeline runners, `EMBEDDERS`/
  `EmbedderConfig`, `ModalEmbedder`, and `run_lifecycle` into the methods
  that construct/dispatch jobs. After this, importing and running any modal
  path never imports torch or transformers client-side. Job construction
  uses plain kwargs/dict-shaped payloads already; no torch-typed values are
  passed client-side (verify during T3 — see §5 risk R2).
- `runtime/base.py`, `runtime/factory.py`: unchanged (already clean).

### 3.4 Deliberately NOT changed

- `polars`/`pandas` imports stay module-level across `data/*`: both load in
  well under a second, they underpin nearly every data module, and threading
  them through every function would triple the diff for marginal gain. They
  stop loading eagerly anyway for commands whose pipelines are now deferred.
- `seaborn`/`sklearn` are not individually touched: they arrive only via
  `training/tracking/*` and `data/pipeline/engineer.py`, which are now
  deferred transitively by §3.2–§3.3.
- `builders/`, `utils/`: unchanged unless the T1 inventory finds a heavy
  transitive import (expected none).

### 3.5 New structural test

`tests/test_cli_import_weight.py`:

- subprocess `python -c "import main"` with `PYTHONPATH=src`; assert
  `torch`, `transformers`, `mlflow`, `seaborn`, `sklearn` absent from the
  printed `sys.modules` snapshot and wall-time under a generous ceiling
  (e.g. < 3s) to catch regressions without flaking.
- subprocess simulating the modal dispatch surface (import
  `runtime.factory` + build a modal runtime with stub env) asserting torch
  is absent from `sys.modules`.
- direct import of `apps.train`/`apps.preprocess` asserting the two
  deliberate side effects still fire at module import (filterwarnings set;
  TOKENIZERS_PARALLELISM exported).

## 5. Risks

- **R1 Import-order behaviour change:** covered by T1 inventory plus the two
  preserved side effects (§2). If T1 finds others, they stay put.
- **R2 Hidden torch-typed job fields:** if any Job dataclass field is typed
  with a torch type and instantiated client-side in the modal path, §3.3
  breaks. Mitigation: T4 asserts torch absence after constructing each modal
  job; convert such annotations to plain `str`/`Any` only if they turn out to
  be unused at client scope — no silent dtype coercion allowed.
- **R3 `get_type_hints` on stringified annotations:** audited safe today
  (§3.1 guard comment); the new test does not cover future call sites — the
  comment at both dataclasses is the tripwire.
- **R4 pyright strictness:** stringified annotations must keep resolving via
  `TYPE_CHECKING` blocks; pyright gate in CI catches drift.

## 6. Acceptance

- `text-forecast --help` and unknown-flag errors return in well under a
  second on a cold interpreter.
- Full pytest suite passes unchanged except the added structural test.
- `--runtime modal` train/eval/preprocess dispatch completes on a machine
  with torch uninstalled-or-unimportable up to the point of network handoff
  (or, minimally, the T4 sys.modules assertion holds).
