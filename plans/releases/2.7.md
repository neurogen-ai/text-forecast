# Plan 2.7 — Distributed GPU training and evaluation

> **Scope:** refactor the train/eval pipelines from plan 2.0 so that a single
> experiment can train/evaluate across **multiple GPUs** — locally and on
> Modal — without any change to experiment files or app code.
>
> Reserved from the original project notes: "the 2.x pipelines will need to
> be refactored to allow for distributed GPU training/eval."
>
> **Prerequisites:** plan 2.0 is complete — `run_train_pipeline` /
> `run_eval_pipeline` exist, the `Engine` runs headless-capable, and the
> runtime dispatch boundary is stable. This plan changes the *inside* of the
> pipelines and Engine; the app → runtime → pipeline call chain is untouched.
>
> This is a v2.x release: parallelism is *how the code runs*, never *what it
> computes* (plan 1.0 B1), so the public contract (experiment files, CLI) does
> not break.

---

## 1. Goal

`citef train` runs multi-GPU with one knob:

- **local:** `citef train -s smoke --gpus 2` (or `[runtime.local] gpus = 2`)
  spawns a DDP group on the local machine.
- **modal:** `citef train -s prod --runtime modal` with
  `[runtime.modal] train_gpu = "A10G:4"` runs the same job on a 4-GPU Modal
  container.

The experiment file, the CLI surface (one additive flag), and the
`Runtime` protocol are unchanged. Single-process behaviour (`gpus = 1`,
the default) must remain bit-for-bit the current behaviour.

---

## 2. Principles

| # | Principle |
|---|---|
| P1 | **Parallelism is a runtime concern.** World size/rank arrive via `RunContext`/job fields — experiment files never learn about ranks (extends plan 2.0 P1). |
| P2 | **Single-process parity.** With `n_gpus == 1` every code path degrades to exactly the plan-2.0 behaviour; no distributed imports are required to run. |
| P3 | **Rank-0 side effects.** Checkpoints, MLflow logging, artifact exports, and progress reporting happen on rank 0 only. |
| P4 | **Same pipelines, sharded inside.** `run_train_pipeline`/`run_eval_pipeline` keep their signatures; sharding lives in Engine/strategy/samplers. |
| P5 | **Single-node first.** Multi-GPU in one container/machine (DDP). Multi-node clusters are explicitly out of scope (v3.0 candidate). |

---

## 3. Current constraints (post-2.0 baseline)

- `Engine` owns a single-process epoch/batch loop over
  `experiment.train_loader` / `val_loader`.
- The strategy builds optimizer/scheduler in `__init__` against
  `model.parameters()` and applies `mat_mul_precision` at construction.
- Experiment samplers (`PortionSampler`, `AutoBinnedSampler`) are plain torch
  samplers with **no rank sharding** (see also plan 1.0 F-7 for sampler
  reseeding semantics).
- The tracker accumulates per-process stores and logs directly to MLflow —
  with N ranks this would log N duplicate/conflicting metric series.
- `MlflowCheckpointProcessor.save` called from every rank would write N
  copies of the checkpoint artifact.
- Modal: `ModalTrainingGPU` requests one GPU (`train_gpu = "A10G"`); Modal
  supports multi-GPU containers via `gpu="A10G:4"`-style requests.

---

## 4. Implementation steps

### S1. Runtime/job surface

1. `RunContext` gains `world_size: int = 1` and `rank: int = 0`
   (runtime = *how it runs*, so this is the correct home).
2. `TrainJob`/`EvalJob` gain `n_gpus: int = 1`. The CLI gets `--gpus`
   (train/eval), defaulting to `[runtime.local].gpus` /
   `[runtime.modal].train_gpu` count.
3. No protocol change to `Runtime`; `LocalRuntime`/`ModalRuntime` read
   `job.n_gpus` and dispatch accordingly.

### S2. Strategy distributed hooks

1. `Strategy` protocol gains two optional hooks:
   `setup_distributed(*, world_size: int, rank: int) -> None` and
   `teardown_distributed() -> None`, with no-op defaults on `BaseStrategy`.
2. A DDP mixin (e.g. `src/training/strategies/ddp.py`) implements them:
   `torch.distributed.init_process_group(backend="nccl" | "gloo")`, wrap
   `self.model` in `DistributedDataParallel` **after** experiment `build()`
   and optimizer construction, and `destroy_process_group()` on teardown.
3. Batch-loss reporting in `training_step` stays per-rank; epoch-level
   reduction happens in the tracker (S4).

> **Correction:** the opt-in DDP mixin described above was superseded during
> implementation — `BaseStrategy.setup_distributed` always performs the DDP
> wrap when `world_size > 1`, delegating the torch-specific wrapping to
> helpers in `src/training/strategies/ddp.py`; nothing opts in; see
> `plans/implementation/v2.7.md`.

### S3. Engine sharded loop

1. When `runtime.world_size > 1`, the Engine wraps the experiment's sampler in
   `torch.utils.data.DistributedSampler` (or shards indices manually when the
   sampler cannot be wrapped) and rebuilds the train loader per epoch, calling
   `set_epoch(epoch)` for deterministic reseeding.
2. Progress bars advance on rank 0 only (already rank-gated via the reporter
   in 2.8, or the `progress is None` guards from 2.0 §11).
3. Checkpoint saves in `Engine.fit` are gated on `rank == 0`.

### S4. Tracker aggregation

1. Keep per-batch CPU stores per rank (unchanged).
2. At `calc_metrics`, all-gather store tensors to rank 0
   (`torch.distributed.all_gather` into padded buffers, or
   `all_gather_object` for simplicity at these sizes) before computing metrics.
3. `log_batch_metric` and `report` emit on rank 0 only.
4. Watch best-threshold metrics (`binary_classification_tracker`): they must be
   computed on the *gathered* stores, not averaged per-rank.

### S5. Checkpointing and resume

1. Rank 0 saves through the existing `MlflowCheckpointProcessor` — no
  processor changes; DDP model state is unwrapped (`model.module.state_dict()`)
  so checkpoints stay compatible with single-process resume.
2. On resume, every rank loads the same MLflow artifact first, then DDP
   broadcasts parameters at wrap time — no special multi-rank load path.
3. MLflow run lifecycle is unchanged: client-created run (2.0 P6), resumed in
   the container/process group; only rank 0 logs.

### S6. Local and Modal dispatch

1. `LocalRuntime.run_train`: for `n_gpus > 1`, launch via
   `torch.multiprocessing.spawn` (or `torchrun` subprocess — pick spawn for
   in-process testability) with one process per GPU, each calling
   `run_train_pipeline` with its `rank`/`world_size` in `RunContext`.
2. `ModalRuntime.run_train`: pass `gpu=f"{gpu_type}:{n_gpus}"` to the Modal
   class, then spawn the same per-rank fan-out inside the container.
3. Eval: for small eval workloads replicating on one GPU is acceptable;
   otherwise partition the eval *windows* (plan 2.0 §9.2 loop) or the window
   batches across ranks, with rank-0 artifact exports.

### S7. Experiment files: no changes

Explicitly verify: both existing experiments train identically single-process
after this lands. Nothing in `src/config/experiments/` may reference ranks.

> **Warning:** implementation branch E (`plans/implementation/v2.7.md`,
> `engine.py` progress plumbing and its rank-0 gating) overlaps with plan 2.8
> (remote progress reporting); if the two are interleaved they must be
> coordinated — serial execution is safe.

## 5. Verification

```bash
# Single-process parity (must match plan-2.0 behaviour exactly)
citef train -s smoke --no-gpu --subsample 512

# Local 2-process CPU smoke (gloo backend) — loss parity within tolerance
citef train -s smoke --no-gpu --subsample 512 --gpus 2

# Local multi-GPU smoke
citef train -s smoke --subsample 512 --gpus 2

# Modal multi-GPU smoke
citef --experiment graph_embed_class train -s smoke --subsample 512 --runtime modal   # train_gpu = "A10G:2"

# Resume a multi-GPU checkpoint on a single process (and vice versa)
citef train -s resume --load-id <ddp-run-id> --load-epoch <n> --no-gpu
```

Expected:

- One MLflow run with one metric series (rank-0 only), no duplicate
  checkpoints.
- DDP checkpoints resume into single-process runs unchanged.
- `basedpyright` strict stays clean; `torch.distributed` imports are lazy so
  single-process runs on machines without NCCL still work.

---

## 6. Non-goals

- **Multi-node clusters** (v3.0 candidate; Modal multi-node training is a
  separate infrastructure project).
- **FSDP / model sharding** (only needed when models stop fitting on one GPU;
  design the S2 hooks so FSDP can replace DDP later).
- **Hyperparameter sweeps** (plan 1.0 F-4).
- Pipeline-parallel or async-SGD variants.

---

## 7. Open questions for the owner (answer before implementation)

- **Q1.** DDP via `mp.spawn` vs `torchrun` for local runs — spawn is proposed
  for testability; any objection?
- **Q2.** Eval sharding: is replicating eval on a single GPU acceptable for
  now (eval is inference-only and much cheaper), or must windows be
  partitioned across ranks immediately?
- **Q3.** Tracker aggregation: is all-gather at epoch boundary acceptable, or
  do you want streaming per-rank reductions for very large eval stores?
- **Q4.** Should `[runtime.modal]` expose separate `train_gpu` count vs type
  (`train_gpu = "A10G"` + `train_gpu_count = 4`) instead of the `"A10G:4"`
  string?
