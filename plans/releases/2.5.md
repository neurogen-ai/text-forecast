The engine currently takes `progress: ProgressBars | None`. In a spawned Modal
container that is `None`, so nothing reports until metrics land in MLflow.
This plan introduces a venue-independent reporter interface that the Engine
and tracker reporting paths call instead of checking for `None`:

- A minimal `Reporter` protocol with heartbeat/progress/metric hooks.
- A local implementation wrapping the existing rich progress bars.
- A remote implementation that batches updates and flushes them to MLflow
  (metrics first, per the owner's preference), so a detached run is followable
  via `mlflow` or `modal.FunctionCall.from_id` while it executes.

## 5. Future steps

- **F-34. Status endpoint / web surface.** If MLflow batching proves too slow
  for interactive following, promote the reporter to POST heartbeats to a
  lightweight endpoint (ties into plan 2.3 §8 web endpoints).
- **F-35. ETA/heartbeat-based hang detection.** Feed reporter heartbeats into
  the plan-2.3 §6.2 health checks to detect hung containers automatically.
