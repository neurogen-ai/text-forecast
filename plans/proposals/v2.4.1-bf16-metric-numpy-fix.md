# Proposal: v2.4.1 — bf16 metric stores crash numpy

Release: v2.4.1 (patch: fixes with no user-visible contract change, per the
numbering convention in plans/releases/README.md)

Status: proposed (not implemented)

## Context

The owner's first bf16 run died at the end of the first eval epoch:

```
File "src/training/engine.py", line 128, in eval_epoch
    self.experiment.tracker.calc_metrics(prefix="val", step=epoch)
File "src/training/tracking/binary_classification_tracker.py", line 243, in calc_metrics
    probs=probs.squeeze(-1).numpy(),
TypeError: Got unsupported ScalarType BFloat16
```

The chain: when a run sets `--dtype bf16`, the strategy feeds
`torch.sigmoid(out.logits.detach().clone())` in bf16
(src/training/strategies/classification.py:65 for train, :100 for val).
`MetricTracker._process_value` stores `value.detach().cpu()` and keeps the
dtype (src/training/tracking/metric_tracker.py:97-106). `calc_metrics` then
calls `.numpy()` on the gathered tensors, and numpy has no bfloat16.

The traceback's line 243 is only where the run finally died. The earlier
`.numpy()` calls in the same function sit inside `try/except` blocks, so the
roc_auc, PR_AUC, and MAE failures were swallowed and logged; the run lost its
metrics silently and then crashed on the one unguarded call, the plot feed at
src/training/tracking/binary_classification_tracker.py:243. The same crash
awaits the train prefix, which the engine also evaluates
(src/training/engine.py:159), and the store export, which calls
`all_values.numpy()` inside `_gather_store`
(src/training/tracking/metric_tracker.py:141). Grep counts 61 `.numpy()`
call sites across the five tracker subclasses
(binary_classification, classification, ordinal_regression,
heteroscadastic_regression, regression), all consuming `_gather_store`
output or tensors derived from it.

Scope note: on committed HEAD this crash cannot reproduce. `RunContext.dtype`
pins fp32 until the 2.4.0 compute-dtype plumbing (currently uncommitted
working-tree changes, proposed in
plans/proposals/v2.4.0-expanded-query-search-strat.md-compute-dtype.md)
reaches a run. This patch is therefore a forward fix for that plumbing. The owner
renumbered it from v2.3.2 to v2.4.1: nothing at 2.3.x can produce a bf16
store, so a 2.3 patch number would claim a fix for a crash that release
cannot reach. The call is recorded under Open decisions.

There is no research note; plans/research/ is empty, and the repo has no PRD.
Evidence: the traceback above, the store pipeline cited line by line, and the
grep inventory of `.numpy()` call sites.

## Features

- Bfloat16 stores convert to fp32 at the
  `_gather_store` boundary in src/training/tracking/metric_tracker.py, so
  every metric computation, plot, and the export `np.save` in all five
  tracker subclasses receive numpy-supported dtypes, for both prefixes.
- One regression test, in a new tests/test_metric_tracker.py: a bf16 store
  round-trips `_gather_store` to numpy without raising, and the export path
  writes an fp32 .npy. The tracker construction and mlflow stubbing follow
  the pattern tests/test_tracker_arity.py already establishes.

## Architecture decisions

- AD1. The fix lives at the gather boundary, the single read path every
  tracker calculation already crosses (no code outside metric_tracker.py
  touches `tracker.stores`). Rejected alternatives: a `.float()`
  before each of the 61 `.numpy()` call sites (scattered; the export
  path still needs its own fix; every new call site reintroduces the bug);
  conversion at feed time in `_process_value` (metric_tracker.py:97), which
  runs per batch inside the training and validation hot path for stores that
  never reach numpy, and nothing reads the stores except `_gather_store`; and
  feeding fp32 from the strategy's sigmoid sites (classification.py:65, :100).
  The strategy sites are the only feeders, so an fp32 feed would fix the
  export too, but any future feeder reintroduces the bug at its own site, and
  numpy awareness does not belong in the strategy; it is the tracker's job.
- AD2. Convert bfloat16 only; fp32, fp64, fp16, and integer stores pass
  through unchanged. numpy maps fp16 to np.float16, so fp16 stores never hit
  this crash; they pass through with fp16-precision metrics, and the 2.4.0
  plumbing already warns when fp16 is chosen. Rejected alternative:
  converting fp16 alongside bf16. Defensible on precision grounds, but it
  changes the exported .npy dtype for fp16 runs, a behaviour change no run
  exercises today; revisit if an fp16 run ever ships. Rejected alternative:
  an unconditional `.float()` on the
  gathered tensor, which silently downcasts any float64 store to fp32 and
  rewrites the int64 id stores, including the `train_ids` export that 2.3.1
  is adding. Rejected alternative: convert toward `self.dtype`; that is the
  run compute dtype, which in the failing runs is bfloat16, exactly the dtype
  numpy rejects. The constructor docstring already marks `dtype`
  interface-compatibility-only (metric_tracker.py:44).
- AD3. bf16 to fp32 is value-exact, so metric values on a bf16 run equal what
  bf16 numpy would have produced had numpy accepted it, and the patch label
  holds. Rejected alternative: computing probabilities in fp32 at the model
  boundary so stores are fp32 natively. That changes the stored values
  (sigmoid of a bf16 logit computed in fp32 differs from bf16 sigmoid upcast)
  and moves a dtype decision into model code for a problem owned by the
  numpy boundary.

## Risk assessment

Friction points:

- MINOR. One transient fp32 copy of a gathered store during conversion,
  roughly double that store's size for the concat-plus-convert moment. Store
  sizes are example-count by small dims, tens of KB to low MB per epoch at
  current shapes (14,853 examples). Absorbed by existing buffers.
- MINOR. The guarded `.numpy()` failures in the owner's traceback mean that
  run reported no metrics before dying. The choke-point fix restores all of
  them at once; the exception-swallowing pattern itself stays untouched and
  remains 2.3.1's `logger.exception` scope.
- MINOR. Reproduction depends on the uncommitted 2.4.0 plumbing only for the
  end-to-end run. The regression test feeds bf16 tensors straight into the
  tracker, so the fix verifies without the plumbing. Sequencing fact, no
  trigger.

No BLOCKING or MAJOR findings. The feature is one conditional conversion in
one function plus a test; there is nothing to descope inside it.

Cost to build:

- Small. One conditional in `_gather_store` and one new test file. Smaller
  than the assert-to-raises branch (Branch D) already specified in
  plans/implementation/v2.5.0.md, the comparator the 2.3.1 proposal also used.
  Constraint: this container has no torch, so the test runs on the owner's
  machine or CI, as the compute-dtype proposal noted for its own test.

Descope triggers, named cuts:

- If tests/test_metric_tracker.py fails on the owner's torch build (a
  `torch.cat` or export failure on bf16 CPU tensors), fall back to converting
  each store element before the concat; the test runs first, before any
  other commit in the series.
- If the owner folds this work into another release (ratify decision below),
  this file closes without implementation and the fix rides that release's
  test plan.

   this patch is a few lines in `_gather_store`.
