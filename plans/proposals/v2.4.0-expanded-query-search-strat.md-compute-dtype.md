# Proposal: compute dtype plumbing (fp32 / bf16 / fp16)

Release: v2.4.0-expanded-query-search-strat. The number was freed by
renumbering the drafted Modal tidy-up chain to 2.5-2.8 (owner decision,
recorded in plans/releases/README.md).

Status: implemented on branch 2.4 (compute dtype plumbing commit; about 70 lines across
src/training/pipeline/_common.py, src/training/pipeline/train.py,
src/apps/train.py, src/models/retrieval_forecast.py, plus a dtype test in
tests/test_pipeline_jobs.py).

## Context

`RunContext.dtype` was pinned to fp32 at src/training/pipeline/_common.py, and
the retriever materialised its stage-2 pool gather in fp32 regardless of
anything downstream. On the owner's Strix Halo (64 GB GPU partition,
docs/strix-halo-container.md) an eval batch's fp32 pool gather was measured at
about 40 GB of the 44.8 GB in use; the bf16 path halves it. The training loop
has no autocast and no GradScaler, which rules out naive fp16.

There is no research note; plans/research/ is empty. Evidence: the dtype
mapping in build_run_context, the pool gather in
src/models/retrieval_forecast.py, and docs/experiments.md's statement that
experiments receive `runtime.dtype`.

## Features

- `--dtype fp32|bf16|fp16` on the train CLI, flowing through `TrainJob` and
  `build_run_context` into `RunContext.dtype`, with a warning when fp16 is
  chosen because the strategy has no GradScaler.
- The retriever's db buffer and stage-2 pool gather live in the compute
  dtype; the stage-1 top-k score matrix and the CLaRa softmax/log-mask loop
  stay fp32 (they are small), so numerics-sensitive code does not move.

## Architecture decisions

- AD1. Params and big tensors in compute dtype, small score matrices in fp32.
  Rejected alternatives: everything fp32 (the 40 GB gather that motivated
  this), and everything in the compute dtype including softmax inputs (the
  log(mask + 1e-6) trick and softmax over tens of thousands of entries
  underflow in fp16 and lose too much in bf16).
- AD2. Explicit dtype end to end, no autocast. Rejected alternative: wrapping
  the strategy in autocast plus GradScaler. That touches every experiment and
  the strategy contract for a gain bf16 already gives; it stays out of scope
  until a proposal asks for fp16 training in earnest.
- AD3. fp16 ships with a warning rather than being refused. Rejected
  alternative: hard error. The owner may want fp16 with a scaler added
  later; a warning plus documentation keeps that door open without
  recommending the path.
- AD4. Eval keeps building its context without a dtype (fp32) for now.
  Rejected alternatives: threading `--dtype` through eval in this release
  (checkpoint loads upcast silently, which is safe; making eval dtype-aware
  is a separate surface change with its own test burden), and recording the
  run dtype in the checkpoint payload so loads reconstruct the right dtype
  automatically. The payload alternative is the durable fix but grows the
  checkpoint format, which this release avoids; it belongs to a follow-up if
  bf16 becomes the default working dtype.

## Risk assessment

Friction points:

- MAJOR. Resuming or evaluating a bf16 run loads weights into an
  fp32-constructed model (eval path, src/training/pipeline/eval.py), so a
  resumed training run in bf16 silently runs fp32 if the operator forgets the
  flag; results differ from the original run's numerics. Contact points:
  load_state_dict call sites in src/training/pipeline/train.py and eval.py.
  Descope trigger: if the owner resumes the current bf16 run and epoch
  metrics shift against the pre-resume trend (checked in the metric_tracker
  table at the resume boundary), either thread dtype through eval in a
  follow-up or cut bf16 from the default run until then; what gets cut is
  bf16 as the working dtype, not the plumbing.
- MAJOR. fp16 gradient underflow in AdamW with no GradScaler. The warning
  mitigates but does not prevent a wasted run. Descope trigger: grad-norm
  probe on the first batches of an fp16 run; if gradients underflow, cut fp16
  from the CLI choices and keep bf16 only.
- MINOR. `self.db.float()` creates a transient fp32 copy of the corpus per
  stage-1 matmul (about 178 MB at 58k rows); the caching allocator absorbs
  it, record and move on.
- MINOR. bf16 matmul behaviour on ROCm/Strix Halo under `mat_mul_precision =
  "high"` differs from fp32 baselines in the last digits; and bf16 plus
  `--compile max-autotune` is untested in this repo (docs/strix-halo-container.md
  covers the fp32 era only). The candidate-strategy proposal's compile probe
  should run one bf16 compiled step alongside its strategy probe, so both
  unknowns settle in the same script.

Cost to build:

- Small, and spent: the code exists uncommitted with one test. Remaining: a
  self-test run of src/models/retrieval_forecast.py on the owner's torch
  install (this container has no torch) and the commit.

Descope triggers, named cuts:

- fp16 underflow confirmed by the grad-norm probe: cut fp16, ship fp32 and
  bf16.
- Resume numerics drift traced to the eval dtype gap: cut bf16 as the working
  dtype until eval takes `--dtype`; the plumbing and fp32 path stay.
