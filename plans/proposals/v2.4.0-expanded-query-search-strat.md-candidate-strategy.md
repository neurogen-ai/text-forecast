# Proposal: candidate strategy for stage-1 pool selection

Release: v2.4.0-expanded-query-search-strat. The number was freed by
renumbering the drafted Modal tidy-up chain to 2.5-2.8 (owner decision,
recorded in plans/releases/README.md). The release title names only this
topic; corpus-scope and compute-dtype ride along already coded, so the
release doc should say so (owner call on the final name).

Status: proposed (not implemented; the only topic in this release with no
working-tree code)

## Context

Plan 2.3 (plans/releases/2.3.md) fixed stage-1 selection as exact nearest
neighbours: `torch.topk` over the date-masked fp32 score matrix in
`VectorRetriever.search`, and exact `IndexFlatIP` on the FAISS path. Every
candidate is always one of the k closest eligible rows. The 2.3 release doc
records the deliberate choice of one exact code path; this proposal widens it
without breaking it.

There is no research note and no prior art for this topic anywhere in the
repo; it is the release's reason to exist and its only real build risk. The
closest repo evidence is the 2.3 release doc, the pool/ladder/ST subset of
tests/test_retrieval_store.py (about 11 of its 18 tests pin nearest-path and
ladder behaviour; the rest cover date emission, collate, and the dim guard),
and the CLaRa ST loop
in src/models/retrieval_forecast.py, which re-scores whatever pool it is
given, so pool composition is the only degree of freedom this feature touches.

## Features

- `candidate_strategy` on `RetrievalModelConfig`: `nearest` (default, exactly
  current behaviour), `random` (uniform over date-eligible rows), `mixed`
  (nearest majority plus a seeded random minority at one fixed default
  ratio; no tunable knob until a second use case exists).
- Random/mixed pools seeded deterministically per batch from the batch's
  example ids, so pool selection is a pure function of (batch ids, corpus
  state) and survives checkpoint resume without growing the checkpoint
  format.

## Architecture decisions

- AD1. Strategy applies inside `VectorRetriever.search`, after the
  date-eligibility mask and the relaxation ladder. Rejected alternatives:
  strategy in `VectorStoreDataset.search`, which has no per-example dates and
  cannot preserve pool purity, and would put a second search-semantics code
  path beside the one 2.3 deliberately unified; and a sampler in
  src/data/samplers/, the repo's home for selection strategies, which exists
  to pick training examples, not db rows, and has no access to the
  eligibility mask or the pool-width ladder that live in the model.
- AD2. Default stays `nearest`. Rejected alternative: making `mixed` the
  default. Flipping the default changes results for every existing config and
  turns a minor release into a breaking one; the 2.3 baselines
  (RetrievalForecast-cited-gr-1-theta-5) must stay reproducible.
- AD3. Random selection perturbs the masked fp32 scores with seeded Gumbel
  noise and reuses the existing `torch.topk`, seeded deterministically per
  batch from the batch's example ids. Rejected alternatives:
  `torch.multinomial` without replacement over the eligibility matrix (a
  graph-break-prone op with CUDA row-count limits at k_pool up to 25k, and a
  shape the compile path already struggles with), host-side sampling of index
  lists (a per-row host sync at B*N = 512 rows per batch), and unseeded or
  per-run-global seeding (runs stop being reproducible across checkpoint
  resume, and the checkpoint payload provably carries no RNG state:
  src/training/checkpointing/mlflow_store.py stores model, epoch, optimizer,
  and scheduler only).
- AD4. `mixed` builds one pool: top nearest rows plus a Gumbel-perturbed
  random fill at one fixed ratio, not two concatenated pools. Rejected
  alternatives: nearest pool and random pool side by side (doubles the pool
  gather, already the largest tensor in the model at about 20 GB bf16 on the
  58k-row corpus), and a tunable ratio knob (one stated use case; add the
  knob when a second use case exists).
- AD5. Standalone `furthest` does not ship. A pool of worst matches makes the
  CLaRa straight-through gradient a pure negative signal and the forward pass
  trains the predictor on deliberately wrong neighbours. `furthest` survives
  only as a mix component if a future proposal wants hard negatives. This cut
  overrides the owner's original "maybe even furthest" ask, so it is flagged
  for owner confirmation at ratify rather than treated as settled. Rejected
  alternative: ship it gated and documented. A flag whose only honest use is
  "never for the main run" is config surface we maintain for nothing.

## Risk assessment

Friction points:

- MINOR. Dynamic pool width (`k_pool`, the batch-minimum eligible count)
  already varies per batch and feeds `torch.compile` with changing shapes
  today; strategy selection does not change width logic. Existing abstractions
  absorb it.
- MAJOR. Recompile churn under `--compile max-autotune`: the Gumbel-perturbed
  topk must survive the compile path, and per-batch width variation already
  triggers recompilation. Contact points: src/models/retrieval_forecast.py
  search(), the model.compile call in src/training/pipeline/train.py.
  Descope trigger: a probe script on the Strix Halo venue compiles one
  training step per strategy; if the Gumbel path graph-breaks or recompiles
  beyond a handful of shapes, fall back to fixed-width padded pools; if
  padding alone does not fix it, cut non-nearest strategies and ship this
  topic as the fixed-width nearest refactor only.
- MAJOR. Random and mixed pools lower stage-1 recall, and the tracker may
  show it. Contact points: training.tracking metric_tracker, epoch-1 eval AUC
  of the existing experiment. Descope trigger: if mixed at the proposed ratio
  lands worse than the nearest baseline at equal epochs on the val window
  (checked by the epoch-1 tracker table), cut random and mixed; the release
  then reduces to topics corpus-scope and compute-dtype.
- MINOR. Resume reproducibility is resolved by design: per-batch seeds derive
  from example ids, so a resumed run selects the same pools for the same
  batches regardless of RNG state, which checkpoints do not carry (verified:
  src/training/checkpointing/mlflow_store.py stores model, epoch, optimizer,
  scheduler only). The residual gap is dataloader order on resume, which
  changes which examples share a batch and therefore the mixed-ratio
  composition, not the mechanism. Record in run notes; no trigger.
- MINOR. Furthest removal is a scope cut made in this proposal, before build,
  so reversing it at ratify costs nothing but a risk line.

Cost to build:

- Small. One selection branch in search() plus config validation, tested by
  extending the pattern test_retrieval_store.py already establishes
  (pool-exclusion and ST-forward checks). Smaller than the delta ladder that
  2.3 absorbed.

Descope triggers, named cuts:

- Compile friction unresolvable after the padded-pool fallback: cut random
  and mixed; release keeps corpus-scope and compute-dtype topics.
- Recall regression at equal epochs: cut random and mixed.
- Owner declines the standalone-furthest cut: furthest returns as a gated
  strategy with its own risk line; nothing else changes.

## Vetting record

Oracle vetting folded in: Gumbel-top-k adopted as the sampling mechanism,
dissolving the multinomial compile risk; checkpoint payload verified to carry
no RNG state, so deterministic per-batch seeding moved from contingency to
design; the mixed ratio knob cut to one fixed ratio; sampler-package
rejection reason added to AD1; test count corrected; numbering collision
resolved by the renumber; release-naming note added to the header;
standalone-furthest cut flagged as an owner decision. No finding was
rejected.
