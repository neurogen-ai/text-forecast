# Proposal: v2.3.1 — MLflow logging fixes

Release: v2.3.1 (patch: fixes with no user-visible contract change, per the
numbering convention in plans/releases/README.md)

Status: ratified 2026-09-06 (not implemented); see the Decided line at the
end of this file

## Context

Two defects in how runs talk to MLflow, both visible in the 2026-09-06 run on
the Strix Halo venue:

1. The tracker log filled with `Store train_ids contains no values, resetting`
   at ERROR level, nine times during one day
   (logs/training.tracking.metric_tracker.log). Root cause verified in the
   repo: `ClassificationStrategy.training_step` feeds `train_y`, `train_logits`,
   and `train_probs` (src/training/strategies/classification.py:44, 64) but
   never `train_ids`, while `BinaryClassificationTracker.calc_metrics`
   unconditionally gathers `{prefix}_ids` for both prefixes
   (src/training/tracking/binary_classification_tracker.py:195), and
   `MetricTracker._gather_store` logs an empty store at ERROR
   (src/training/tracking/metric_tracker.py:145). The validation path feeds
   `val_ids` (classification.py:89); the train path was simply never wired.
2. `run_eval_pipeline` calls `mlflow.start_run(run_id=...)` before
   `mlflow.set_tracking_uri(...)` (src/training/pipeline/eval.py:148-149). The
   train pipeline does it in the correct order (train.py:103-105). start_run
   resolves the run against the previously configured store, so eval runs can
   land on a stale or default tracking URI depending on process history.

Adjacent log-quality defect, same package: the tracking code swallows
exceptions with a bare `logger.error(e)` scattered through metric_tracker.py
(:188, :206, :261) and binary_classification_tracker.py (:90, :99, :108,
:122, :183, :214, :224, :254, :260, :266, and more below) — grep, do not
trust ranges — which logs exception messages with no traceback and no
context.

## Features

- Feed `train_ids` from `training_step` so the train path carries the same id
  tracking the validation path already has, skipping the feed when the batch
  carries the NaN fallback ids.
- Downgrade the empty-store message in `_gather_store` from ERROR to DEBUG:
  an empty store after a guard is an expected condition, not an error.
- Reorder `set_tracking_uri` before `start_run` in `run_eval_pipeline`.
- Replace bare `logger.error(e)` in the tracking/MLflow paths with
  `logger.exception` plus a context string.

## Architecture decisions

- AD1. Fix by feeding the store, not by deleting or conditionally skipping
  the gather. Rejected alternatives: remove the `{prefix}_ids` gather from
  `calc_metrics`, or skip the gather when the store is empty at the call site
  (binary_classification_tracker.py:195). The val path feeds ids today and
  five tracker subclasses define the same store names
  (binary_classification_tracker.py:40, classification_tracker.py:39,
  heteroscadastic_regression_tracker.py:156, ordinal_regression_tracker.py:115,
  regression_tracker.py:117); both rejected fixes silence the symptom while
  leaving the train/val id asymmetry in place.
- AD2. Feed unconditionally except when the batch carries the NaN fallback:
  `TokenBatch.id` is typed non-optional (src/data/datasets/types.py:29) and
  `TextTokenDataset.__getitem__` emits a NaN fallback tensor when
  `return_id=False` (src/data/datasets/text_token_dataset.py:184-186, collated
  unconditionally at :240). So there is no None case to guard, and at least
  one train config sets `return_id=False` (graph_embed_class.py:81): feeding
  NaN ids lands in `_process_value`, which logs its own ERROR and skips
  (metric_tracker.py:133-137) — the patch would swap one ERROR-spam source for
  another. The feed therefore skips when `torch.isnan(batch.id).all()`, and
  the NaN-rejection message level gets reviewed in the same pass (a
  fully-NaN id batch is a config fact, not an error). Rejected alternative:
  unguarded `batch.id.clone()` mirroring the val line, which feeds NaN on
  every `return_id=False` batch.
- AD3. Empty-store logging becomes a latched one-time WARNING per store name,
  following the pattern `VectorRetriever._warned_no_candidates` already uses
  (src/models/retrieval_forecast.py). Rejected alternatives: pure DEBUG
  (buries the "eval window matched zero rows" case this message exists for)
  and deleting the message (same problem); per-epoch WARNING (the noise this
  patch removes). One plain line per store name, no counters.
- AD4. The eval tracking-URI fix is a two-line reorder, no API change.
  Rejected alternative: threading an explicit client through the pipeline
  (MlflowClient already exists in the checkpoint processor). Right for a
  larger tracking refactor; wrong for a patch.
- AD5. Bare `logger.error(e)` replacements stay inside the tracking package.
  Rejected alternative: repo-wide sweep. That is a style refactor, not a
  logging fix; it belongs to a minor, not this patch.

## Risk assessment

Friction points:

- MINOR. Feeding `train_ids` grows the gathered train-store tensors by one
  int64 per example (14,853 ids per epoch at current shapes). Absorbed by
  existing buffers.
- MINOR. Metric payloads change slightly: `train_ids` now exports with the
  other train stores when export is enabled (metric_tracker.py:135-137 adds
  a `train_ids.npy` to the debug export payload). No metric names or values
  change; consumers of the exported arrays gain a column. Not a documented
  contract, so the patch label survives; record in the commit, no trigger.
- MINOR. The tracking-URI reorder changes behaviour only for processes where
  a stale URI was set; those runs were writing to the wrong store and were
  broken. No trigger.

Cost to build:

- Small. Two feed-lines plus a guard in classification.py, one level change
  in metric_tracker.py, a two-line reorder in eval.py, and mechanical
  logger.exception swaps. Smaller than the assert-to-raises task (T4) already
  specified in the 2.5 implementation plan.

Descope triggers, named cuts:

Descope triggers, named cuts:

- If the NaN-id path proves unavoidable per experiment config (a train
  config that mixes real and fallback ids inside one batch), cut the
  feed-lines and ship the latched-warning downgrade plus the URI reorder;
  checkable in the first commit by inspecting id tensors across the existing
  experiment configs.
- If `logger.exception` swaps in the plot paths produce noisy tracebacks per
  eval epoch (check the first eval run's log), cut those swaps and keep the
  fix in `calc_metrics` only.

## Open decision for ratify

Whether the `train_ids` feed rides in this patch or moves to the next minor.
The rest (latched warning, URI reorder, logger.exception swaps) is
unambiguously patch-grade; the feed is data capture that happens to fix the
spam, and it adds a column to the export payload (see risk section). The
proposal's descope structure supports either outcome.

## Vetting record

Oracle vetting folded in, no findings rejected: AD2 rewritten around the
verified NaN-fallback id behaviour (TokenBatch.id is non-optional; the val
path feeds NaN ids rather than crashing), replacing the dead
structural-optionality descope trigger with a NaN-mix one; subclass count
corrected to five; conditional-gather alternative recorded in AD1; latched
one-time WARNING adopted in AD3 over pure DEBUG, with the counter dropped;
bare-error citation replaced with a grep instruction; export-payload note
expanded; the train_ids feed flagged as an owner call at ratify.

Decided 2026-09-06: ratified into plans/releases/v2.3.1.md (train_ids feed
kept in-patch; empty-store level per AD3, latched one-time WARNING, which
