# Proposal: v2.3.1 — MLflow logging fixes

Release: v2.3.1 (patch: fixes with no user-visible contract change, per the
numbering convention in plans/releases/README.md)

Status: ratified 2026-09-06 (pending implementation); see the Decided line
at the end of this file. The v1 ratification was withdrawn the same day when
the release doc was deleted for the param-tracking amendment; the amended
proposal was re-ratified the same day.

## Context

Two defects in how runs talk to MLflow, both visible in the 2026-09-06 run on
the Strix Halo venue:

1. The tracker log filled with `Store train_ids contains no values, resetting`
   at ERROR level, nine times during one day
   (logs/training.tracking.metric_tracker.log). Root cause verified in the
   repo: `ClassificationStrategy.training_step` feeds `train_y`, `train_logits`,
   and `train_probs` (src/training/strategies/classification.py:44, 64) but
   never `train_ids`, while `BinaryClassificationTracker.calc_metrics`
   unconditionally gathers `{prefix}_ids` for both prefixes
   (src/training/tracking/binary_classification_tracker.py:195), and
   `MetricTracker._gather_store` logs an empty store at ERROR
   (src/training/tracking/metric_tracker.py:145). The validation path feeds
   `val_ids` (classification.py:89); the train path was simply never wired.
2. `run_eval_pipeline` calls `mlflow.start_run(run_id=...)` before
   `mlflow.set_tracking_uri(...)` (src/training/pipeline/eval.py:148-149). The
   train pipeline does it in the correct order (train.py:103-105). start_run
   resolves the run against the previously configured store, so eval runs can
   land on a stale or default tracking URI depending on process history.

Adjacent log-quality defect, same package: the tracking code swallows
exceptions with a bare `logger.error(e)` scattered through metric_tracker.py
(:188, :206, :261) and binary_classification_tracker.py (:90, :99, :108,
:122, :183, :214, :224, :254, :260, :266, and more below) — grep, do not
trust ranges — which logs exception messages with no traceback and no
context.

Param-tracking gap, same pipelines: the train run logs four params
(src/training/pipeline/train.py:122-127: experiment_name, model.class,
train.examples, val.examples) and nothing else. The values the owner tunes
or groups runs by are recorded nowhere: base lr and weight_decay live in the
strategy's optimizer spec (src/training/optimizers/specs.py), scheduler
params in src/training/schedulers.py, epochs and the eval/checkpoint
intervals on the Experiment dataclass (src/config/experiment.py:29-31),
batch sizes on the loaders, accumulation_steps and mat_mul_precision on
StrategyConfig (src/training/strategies/base.py:63-69), device, dtype,
compile_mode and subsample on RunContext (src/config/runtime.py), and model
hyperparameters in each model's config dataclass. Per-epoch lr is already a
metric via log_lrs (src/training/engine.py:141); the base value is not.
The legacy helper src/training/tracking/log_params.py dumps config.__dict__
with '-'-joined keys and has no callers; it and _get_scheduler_params.py are
dead code that makes param logging look handled when it is not.

## Features

- Feed `train_ids` from `training_step` so the train path carries the same id
  tracking the validation path already has, skipping the feed when the batch
  carries the NaN fallback ids.
- Downgrade the empty-store message in `_gather_store` from ERROR to DEBUG:
  an empty store after a guard is an expected condition, not an error.
- Reorder `set_tracking_uri` before `start_run` in `run_eval_pipeline`.
- Replace bare `logger.error(e)` in the tracking/MLflow paths with
  `logger.exception` plus a context string.
- Log the full hyperparameter set to the train run at start as flat params
  with readable leaf keys (bare names, suffixed only to disambiguate):
  optimizer spec (base lr, weight_decay), scheduler spec, epochs,
  eval/checkpoint intervals, train/val batch sizes, accumulation_steps,
  mat_mul_precision, examples_per_epoch, device, dtype, compile_mode,
  subsample, dataset sizes, the model's config dataclass where the model
  keeps one, and class names for model/strategy/tracker.
- Delete the unused log_params helper and _get_scheduler_params (dead code
  with no callers).

## Architecture decisions

- AD1. Fix by feeding the store, not by deleting or conditionally skipping
  the gather. Rejected alternatives: remove the `{prefix}_ids` gather from
  `calc_metrics`, or skip the gather when the store is empty at the call site
  (binary_classification_tracker.py:195). The val path feeds ids today and
  five tracker subclasses define the same store names
  (binary_classification_tracker.py:40, classification_tracker.py:39,
  heteroscadastic_regression_tracker.py:156, ordinal_regression_tracker.py:115,
  regression_tracker.py:117); both rejected fixes silence the symptom while
  leaving the train/val id asymmetry in place.
- AD2. Feed unconditionally except when the batch carries the NaN fallback:
  `TokenBatch.id` is typed non-optional (src/data/datasets/types.py:29) and
  `TextTokenDataset.__getitem__` emits a NaN fallback tensor when
  `return_id=False` (src/data/datasets/text_token_dataset.py:184-186, collated
  unconditionally at :240). So there is no None case to guard, and at least
  one train config sets `return_id=False` (graph_embed_class.py:81): feeding
  NaN ids lands in `_process_value`, which logs its own ERROR and skips
  (metric_tracker.py:133-137) — the patch would swap one ERROR-spam source for
  another. The feed therefore skips when `torch.isnan(batch.id).all()`, and
  the NaN-rejection message level gets reviewed in the same pass (a
  fully-NaN id batch is a config fact, not an error). Rejected alternative:
  unguarded `batch.id.clone()` mirroring the val line, which feeds NaN on
  every `return_id=False` batch.
- AD3. Empty-store logging becomes a latched one-time WARNING per store name,
  following the pattern `VectorRetriever._warned_no_candidates` already uses
  (src/models/retrieval_forecast.py). Rejected alternatives: pure DEBUG
  (buries the "eval window matched zero rows" case this message exists for)
  and deleting the message (same problem); per-epoch WARNING (the noise this
  patch removes). One plain line per store name, no counters.
- AD4. The eval tracking-URI fix is a two-line reorder, no API change.
  Rejected alternative: threading an explicit client through the pipeline
  (MlflowClient already exists in the checkpoint processor). Right for a
  larger tracking refactor; wrong for a patch.
- AD5. Bare `logger.error(e)` replacements stay inside the tracking package.
  Rejected alternative: repo-wide sweep. That is a style refactor, not a
  logging fix; it belongs to a minor, not this patch.
- AD6. Params are logged from the materialized Experiment and RunContext in
  the train pipeline, not from the config source modules. The config
  functions build objects from module constants and kwargs; the materialized
  objects are the one place every resolved value already exists. Rejected
  alternatives: reviving the dead log_params helper (dumps raw __dict__,
  no callers, wrong key scheme) and parsing the config module source.
- AD7. A generic scalar walker collects candidate values by recursing into
  dataclasses and pydantic models (optimizer/scheduler specs,
  StrategyConfig, the model's config), keeping only str/int/float/bool and
  stringifying other objects as class names. Param keys are bare leaf names
  by default (lr, epochs, embed_dim) so MLflow param search and the compare
  view hit on the readable name. Ambiguous leaves (the same name from more
  than one component: embed_dim in the embedder and forecaster configs,
  batch_size on the train and val loaders) are disambiguated leaf-first:
  embed_dim-embedder, embed_dim-forecaster, batch_size-train,
  batch_size-val. The existing four keys fold into the scheme as
  experiment_name, model_class, examples-train, examples-val. Rejected
  alternatives: prefixed dotted keys (model.embed_dim; hides the leaf the
  owner wants searchable) and bare names only (duplicate keys with different
  values raise in MLflow, forcing exactly the deduping and renaming the
  scheme avoids).
- AD8. Model hyperparameters are captured by convention: models keep their
  constructor config as `self.config`, verified in 20 of the 21 model
  families in src/models/, and the walker flattens it. graph_recurrent.py
  stores its hyperparameters as plain attributes and rides as
  class-name-only until it gains a config dataclass. Rejected alternative:
  introspecting constructor signatures or nn.Module internals; the latter
  leaks weights and buffers into the param table.
- AD9. Params are logged once at run start inside the existing start_run,
  and eval keeps its eval.*-prefixed params (eval.py:154) untouched. MLflow
  params are immutable per run and the train pipeline reuses job.run_id on
  resume, so the log call is guarded: identical values are a no-op, changed
  values log a warning instead of raising. A mismatch on resume means the
  operator should have taken a new run_id, which the parent CLI flags
  already provide; the guard records that misuse without killing the run.
  Rejected alternative: logging hyperparameters as tags; params are the
  MLflow-native bucket for run configuration and drive the compare view.
- AD10. The disambiguation lives in an explicit rename table in its own
  small module, separate from the generic walker, so renaming or adding a
  key is a one-place edit and every non-bare key is visible in one list.
  Ambiguous leaves log both the bare key and all suffixed keys on every
  run, regardless of whether the values happen to match, so the key set is
  identical across runs; the compare view breaks when keys appear and
  disappear between runs. This duplication is the owner's stated
  preference.

## Risk assessment

Friction points:

- MINOR. Feeding `train_ids` grows the gathered train-store tensors by one
  int64 per example (14,853 ids per epoch at current shapes). Absorbed by
  existing buffers.
- MINOR. Metric payloads change slightly: `train_ids` now exports with the
  other train stores when export is enabled (metric_tracker.py:135-137 adds
  a `train_ids.npy` to the debug export payload). No metric names or values
  change; consumers of the exported arrays gain a column. Not a documented
  contract, so the patch label survives; record in the commit, no trigger.
- MINOR. The tracking-URI reorder changes behaviour only for processes where
  a stale URI was set; those runs were writing to the wrong store and were
  broken. No trigger.
- MINOR. MLflow caps param key and value lengths; the walker truncates
  stringified values rather than raising. Only exotic fields can hit this.
- MINOR. On resume with a changed config, the guarded param log keeps the
  original run's values and warns. That is arguably the correct record (the
  original config is what produced the checkpoint) and no run crashes.
- MINOR. StrategyConfig holds live objects (model, tracker, stream, device);
  the walker's scalar filter must skip them or run start raises. Covered by
  AD7, but a new exotic field type is the one way the walker breaks.

Cost to build:

- Small. Two feed-lines plus a guard in classification.py, one level change
  in metric_tracker.py, a two-line reorder in eval.py, mechanical
  logger.exception swaps, plus one scalar-walker helper and its test.
  Smaller than Branch D of plans/implementation/v2.5.md (assert-to-raises),
  the comparator the v1 ratification also used. (The earlier "task T4"
  citation was a stale label, corrected by the v2.3.2 vetting record.)

Descope triggers, named cuts:

Descope triggers, named cuts:

- If the NaN-id path proves unavoidable per experiment config (a train
  config that mixes real and fallback ids inside one batch), cut the
  feed-lines and ship the latched-warning downgrade plus the URI reorder;
  checkable in the first commit by inspecting id tensors across the existing
  experiment configs.
- If `logger.exception` swaps in the plot paths produce noisy tracebacks per
  eval epoch (check the first eval run's log), cut those swaps and keep the
  fix in `calc_metrics` only.
- If the walker raises on any existing experiment config at run start, cut
  the walker and log an explicit hand-written param dict (the four current
  params plus the spec fields); checkable on the first train run of each
  existing experiment config.
- If flattening a model's `self.config` fails to serialize cleanly, cut that
  family back to model_class only. The first-commit model survey has been
  run: 20 of 21 families keep `self.config`, graph_recurrent is listed as
  class-name-only, so only a serialization failure can fire this trigger.

## Open decisions for ratify

All closed at ratify (2026-09-06, across the v1 and re-ratify rounds):

- train_ids feed rides in this patch (owner).
- Empty-store level per AD3, latched one-time WARNING (owner).
- The v2.3.2 bf16 fold declined; that fix moves to v2.4.1 (owner).
- Dead code: log_params and _get_scheduler_params are deleted in this
  patch (owner).
- Grouping: params only, no tags (owner).
- Key scheme: bare leaf names, leaf-first suffix disambiguation, explicit
  rename table, bare-plus-suffixed duplication on ambiguous leaves (owner).
- Resume: guard warns, never raises; a mismatch means the operator should
  have taken a new run_id (owner).

Patch-label check: the param logging adds MLflow data but no code contract
change, so the patch label survives, consistent with the train_ids
export-payload note in the risk section.

verified NaN-fallback id behaviour (TokenBatch.id is non-optional; the val
path feeds NaN ids rather than crashing), replacing the dead
structural-optionality descope trigger with a NaN-mix one; subclass count
corrected to five; conditional-gather alternative recorded in AD1; latched
one-time WARNING adopted in AD3 over pure DEBUG, with the counter dropped;
bare-error citation replaced with a grep instruction; export-payload note
expanded; the train_ids feed flagged as an owner call at ratify.

could ride in this release; the proposal returns to proposed. The v1 owner
decisions stand: train_ids feed kept in-patch, empty-store level per AD3
(latched one-time WARNING, superseding the stale DEBUG wording in Features
above), the v2.3.2 bf16 fold declined (that fix moves to v2.4.1). Codebase
verification added with the amendment: train.py:122 logs four params;
