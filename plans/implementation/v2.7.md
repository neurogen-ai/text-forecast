# Plan 2.7 implementation — remote progress tracking for cloud runs

Implements `plans/releases/2.7.md` against the code as of plan 2.2 (Engine loop
in `src/training/engine.py`, pipelines in `src/training/pipeline/{train,eval}.py`,
runtimes in `src/runtime/local.py` and `src/runtime/modal_runtime.py`). One
branch per PR; each step fits one context window and lands as one commit.

## Context

Today a training run reports progress only through rich progress bars. The
Engine guards every bar call behind `progress is None` (plan 2.0 §11), so a
spawned Modal container runs with `progress=None` and a detached 24h training
run is invisible until epoch metrics land in MLflow. This release replaces the
`None` guards with a `Reporter` interface: a local implementation wraps the
existing bars, a remote implementation batches updates and flushes them to
MLflow so any spawned run is followable while it executes.

**Files touched:** `src/training/reporting.py` (new),
`src/training/engine.py`, `src/training/pipeline/train.py`,
`src/training/pipeline/eval.py`, `src/runtime/local.py`,
`src/runtime/modal_runtime.py`, `src/training/tracking/metric_tracker.py`,
`docs/training.md`,
`docs/apps.md`, `tests/test_reporting.py` (new),
`tests/test_mlflow_reporter.py` (new).

**Depends on documents:** `plans/releases/2.7.md` (the spec),
`plans/releases/2.0.md` §11 (the headless `progress=None` mode being replaced)
and P6/P7 (client-side run creation, spawned dispatch),
`plans/releases/2.5.md` §6.2/§8 (future consumers of heartbeats, referenced by
F-34/F-35 only — not implemented here), `docs/training.md`, `docs/apps.md`.

**Ordering vs other plans:** the only hard prerequisite is plan 2.0 complete.
Plan 2.6 rewires the same plumbing (its E1 hands bars to rank 0 only), so if
2.6 has already merged, branch these off post-2.6 main and nothing here
changes: the Reporter interface says nothing about ranks, and post-2.5 only
rank 0 constructs a reporter. If 2.6 lands first, 2.5's E1 swaps
`build_progress_bars()` for `rich_reporter()` and nothing else.

## Decisions made here

The implementing agent follows these; it does not re-litigate them.

- **D1. Protocol plus three constructors, no class hierarchy.**
  `Reporter` is a `typing.Protocol`; `NULL_REPORTER` (module singleton),
  `rich_reporter()`, and `mlflow_reporter(run_id=...)` are the only
  constructions sites. No `ReporterType` enum, no base class.
- **D2. The Engine never checks `None`.** The default argument is
  `NULL_REPORTER`, whose methods are `pass`. Every `if self._progress is None`
  guard in `engine.py` disappears.
- **D3. MLflow-first, batched by wall clock.** The remote channel is MLflow
  metrics plus one heartbeat tag, flushed at most every 30s. Per-batch calls
  only bump integer counters; nothing hits the network per batch. This matches
  the owner's "metrics first" preference in the release doc.
- **D4. Venue choice stays at the edges.** The pipeline accepts a reporter;
  `LocalRuntime` builds `rich_reporter()`, the Modal container methods build
  `mlflow_reporter(...)`. The pipeline never asks where it runs.
- **D5. Table rendering moves into the reporter.** `MetricTracker.report`
  currently renders a rich table when handed a progress bar. That rendering
  moves to `Reporter.epoch_metrics`; the tracker returns the dict and nothing
  else. The tracker should not know about display.
- **D6. Heartbeat format:** the MLflow tag `progress.heartbeat` holds unix
  seconds as a string, refreshed on every flush. F-35 hang detection reads
  exactly that tag later; nothing else may write it.

## Goals

- A spawned Modal train or eval run logs cumulative `progress.*` metrics and a
  fresh `progress.heartbeat` tag throughout execution, so it can be followed
  with `mlflow` or the MLflow UI while it runs.
- Local runs look and behave exactly as today: same bars, same table output,
  same totals.
- The Engine contains zero `if progress is None` branches.
- Adding a third venue or channel (web endpoint, F-34) means writing one new
  `Reporter` implementation and constructing it at one call site.

## Abstractions introduced, and what each absorbs

- **`src/training/reporting.py`, the `Reporter` protocol.** All progress
  traffic funnels through seven methods. Absorbs: F-34 (a POST-to-endpoint
  reporter is one new implementation), F-35 (hang detection reads heartbeats
  produced here regardless of venue), and any future channel, without touching
  the Engine again.
- **`NULL_REPORTER`.** Replaces every `is None` check with do-nothing methods.
  Absorbs: new optional hooks growing on the protocol without new call-site
  guards.
- **`mlflow_reporter(*, run_id, client=None, now=time.time, flush_interval_s=30.0)`**,
  dependency-injected client and clock. Absorbs: changing flush policy,
  metric names, or switching the transport (tags vs metrics) inside one class;
  tests inject fakes instead of patching MLflow.
- **Table rendering behind `epoch_metrics`.** Absorbs: a remote metrics table
  (log an artifact, print structured text) by editing implementations only.

## Branch A — `feat/reporter-protocol`

### Step A1. The protocol, NULL_REPORTER, and RichReporter

Create `src/training/reporting.py`:

```python
class Reporter(Protocol):
    def epoch_start(self, *, epoch: int, total_epochs: int) -> None: ...
    def train_reset(self, *, total: int) -> None: ...
    def train_advance(self, *, examples: int) -> None: ...
    def eval_reset(self, *, description: str, total: int) -> None: ...
    def eval_advance(self, *, examples: int) -> None: ...
    def epoch_advance(self) -> None: ...
    def epoch_metrics(self, *, epoch: int | None, metrics: dict[str, float]) -> None: ...

NULL_REPORTER: Reporter  # module singleton, every method is `pass`

def rich_reporter() -> Reporter
    # wraps builders.build_progress_bars(); owns the task ids the Engine
    # currently computes in __init__ (Epochs/Train Examples/Eval Examples);
    # epoch_metrics renders the rich.Table exactly as MetricTracker does
    # today (same colours, same Epoch column) via its own Console.
    # close() stops the bars — see Step A3.
```

`Reporter` implementations may expose a `close(self) -> None` method;
callers check `hasattr(reporter, "close")` once in a shared helper
`close_reporter(reporter)` in the same file, so the protocol stays minimal.

Out of scope: any MLflow code, any change to `builders/build_progress_bars.py`,
any caller edits (next steps).

Verify: `pytest tests/test_reporting.py -q` green, where the suite asserts
`NULL_REPORTER` methods return `None` without state, and a `rich_reporter()`
constructed with `build_progress_bars(disable=True)` accepts all calls without
error under a non-TTY console. `pyright src/training/reporting.py` clean.

### Step A2. The Engine drives the reporter

In `src/training/engine.py`:

1. Delete `ProgressBars` and every `_advance`/`_reset`/`_advance_epoch` helper
   including their `None` checks. The constructor takes
   `reporter: Reporter = NULL_REPORTER` and stores it; no task ids live here
   anymore. Import from `training.reporting`.
2. Call sites map one to one onto the old helpers: `train_epoch` calls
   `train_reset(total=self._total_examples(...))` at the top and
   `train_advance(examples=self._batch_size(batch))` per batch;
   `eval_epoch` calls `eval_reset(description="Eval Examples", total=...)` and
   `eval_advance(...)`; `fit` calls `epoch_start(epoch=start_epoch,
   total_epochs=start_epoch + self.experiment.epochs)` before the loop and
   `epoch_advance()` at the end of each iteration.
3. In `fit`, replace the `tracker.report(progress_bar=..., epoch=...)` call
   with `metrics = self.experiment.tracker.report(epoch=epoch)` followed by
   `self._reporter.epoch_metrics(epoch=epoch, metrics=metrics)`. (The tracker
   signature change is step B1; until B merges, pass `progress_bar=None`
   positionally-compatible — i.e. keep calling with keyword `epoch=` only.)
4. The `mlflow.log_metrics(metrics, ...)` call in `fit` is untouched; epoch
   metric upload stays in the Engine, distinct from progress reporting.

Out of scope: eval-pipeline call sites beyond compiling
(`run_eval_pipeline` passes `progress=None` today; step A3 fixes it), the
runtimes, anything in `builders/`.

Verify: `pytest tests/test_headless_engine.py -q` green — extend its fake to
be a `Reporter` recorder asserting the exact call sequence
`epoch_start, (train_reset, train_advance*, eval_reset?, eval_advance*,
epoch_advance)*` for a two-epoch toy experiment. Add the recorder to
`tests/test_reporting.py`. `pyright src/training/engine.py` clean.

4. `ModalTrainingGPU.train`/`.eval` keep calling the pipelines bare

Out of scope: MlflowReporter (branch C), tracker table rendering (branch B),

## Branch C — `feat/mlflow-reporter`  (parallel with B)

### Step C1. The batched MLflow reporter

Append to `src/training/reporting.py`:

```python
def mlflow_reporter(
    *,
    run_id: str,
    client: MlflowClient | None = None,      # injected; default MlflowClient()
    now: Callable[[], float] = time.time,    # injected clock for tests
    flush_interval_s: float = 30.0,
) -> Reporter
```

Behaviour:

- `train_advance(n)` / `eval_advance(n)` increment counters
  (`_train_total`, `_eval_total`) and call `maybe_flush()`. No network per
  batch.
- `maybe_flush()` returns early unless `now() - _last_flush >=
  flush_interval_s`. A flush writes, via the client:
  - `log_metric(run_id, "progress.train_examples", _train_total,
    timestamp=int(now() * 1000), step=_epoch, synchronous=False)`
    (only when the counter moved since last flush; same for
    `"progress.eval_examples"`), and
  - `set_tag(run_id, "progress.heartbeat", str(int(now())))` — always, even
    when no counter moved (decision D6).
- `epoch_start` stores the current epoch for use as metric `step`;
  `train_reset`/`eval_reset` reset their stage counter to 0 (per-epoch totals,
  so the metric series is cumulative-within-epoch; the step axis separates
  epochs).
- `epoch_metrics` forces a flush (epoch boundary is worth a network round
  trip regardless of the timer).
- `close()` performs a final flush. It must tolerate being called twice.

State is private to the closure or a private class; nothing else imports the
counters. Metric names live as module constants
(`PROGRESS_METRICS = ("progress.train_examples", "progress.eval_examples")`,
`HEARTBEAT_TAG = "progress.heartbeat"`) because F-35 will import them.

Out of scope: a web-endpoint reporter (F-34), hang detection consumers
(F-35 / plan 2.5 §6.2), GPU-memory reporting, any config knob for the flush
interval (constant is fine until evidence says otherwise).

Verify: `pytest tests/test_mlflow_reporter.py -q` green. The suite injects a
fake client (records `(key, value, step, timestamp)` tuples and tags) and a
fake clock advanced manually: asserts no calls before the interval, one
heartbeat tag per flush even with zero movement, counters reset on
`*_reset`, forced flush on `epoch_metrics`, idempotent `close()`.
`pyright src/training/reporting.py` clean.
