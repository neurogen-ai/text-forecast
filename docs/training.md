# Training internals

`src/training/` owns everything that happens inside a run: the epoch loop,
strategies, losses, optimizers, schedulers, metric trackers, and checkpointing.
The CLI apps build an `Experiment` and hand it to the Engine; this page explains
what the Engine calls into.

## The Engine (`engine.py`)

The Engine is the only place with an epoch or batch loop. It takes an
`Experiment`, a `RunContext`, and three Rich progress bars (epochs, train
examples, eval examples) passed as `progress`. The bars are optional: pass
`progress=None` to run headless (no TTY), which remote execution uses.
Every `add_task`, `reset`, and `advance` call is guarded behind that `None`
check, so the loop behaves identically either way.

`fit(start_epoch, run_id)` runs this per epoch, in order:

1. Log current LRs to MLflow
2. `train_epoch()` - iterate `experiment.train_loader`, calling
   `strategy.training_step(batch)` per batch
3. `strategy.scheduler_step()`
4. Checkpoint every `experiment.checkpoint_interval` epochs: model + optimizer +
   scheduler state dicts go to `experiment.checkpoints.save(state, run_id)`
5. Eval every `experiment.eval_interval` epochs via `eval_epoch()`
6. Compute `train_*` metrics, call `tracker.report()`, log the returned dict to
   MLflow, then `tracker.clear()`

`eval_epoch(loader=None)` runs `strategy.validation_step` over a loader (the
val loader by default) and computes `val_*` metrics. The eval app reuses it with
windowed loaders.

Progress totals come from the sampler when one exists, otherwise the dataset.
In headless mode the rich table render is skipped too: `tracker.report()`
takes `progress_bar=None` and returns the aggregated metrics dict without
drawing a table.

## Strategies (`strategies/`)

A strategy owns device placement, the per-batch step, and optimizer/scheduler
construction. The contract is the `Strategy` protocol in `base.py`
(Lightning-compatible hook names): `configure_optimizers`, `start_epoch`,
`move_to_device`, `training_step`, `validation_step`, `scheduler_step`,
`load_optimizer_state`.

- **`StrategyConfig`** - Pydantic model with `extra="forbid"` declaring what every
  strategy gets: model, loss_fn, tracker, optimizer spec, scheduler spec, CUDA
  stream, device, `examples_per_epoch`, `accumulation_steps` (default 1), and
  `mat_mul_precision` (default "high"). Runtime values like device are injected;
  experiment-relevant values come from the experiment module.
- **`BaseStrategy`** - shared machinery: sets float32 matmul precision, builds the
  optimizer/scheduler from specs, resets per-epoch counters in `start_epoch`,
  moves nested batch objects to device non-blocking, and restores
  optimizer/scheduler state on resume (accepting live objects or raw state dicts).
- **`ClassificationStrategy`** - the concrete binary-classification strategy.
  Batch layout protocol: `(id, x, y, mask, weight)` tensors; model output must
  expose `.logits` and `.probs`.

Its training step does: stash targets in the tracker, move batch to device under
the CUDA stream, forward, compute loss, divide by `accumulation_steps`, backward,
and take an optimizer step every `accumulation_steps` batches (or at the last
partial step of the epoch). Loss and detached logits/probs go into the tracker;
per-batch loss is also logged as `train_loss-batch`. Validation steps run under
`torch.no_grad()` with `val_*` prefixes.

New task types mean new strategies: implement `BaseStrategy` for the batch/model
protocol you need, following `classification.py`.

## Optimizers and schedulers

Optimizer and scheduler choices are dataclass specs rather than live objects so
experiments can declare them declaratively:

- `optimizers/specs.py` - `OptimizerSpec` protocol plus `AdamWSpec(lr, weight_decay)`
- `schedulers.py` - `LRSchedulerSpec` protocol plus two warmup+cosine specs:
  - `WarmupCosineSpec` - linear warmup over `milestones[0]` epochs, then
    `CosineAnnealingWarmRestarts`; matches the legacy scheduler exactly
  - `WarmupCosineAnnealingSpec` - same warmup, then smooth `CosineAnnealingLR`
    decay to `eta_min`

Both filter milestones below 1 (legacy behaviour), assert milestone sums do not
equal total epochs, and compose phases with `SequentialLR`. Schedulers step once
per epoch, not per batch.

## Losses (`losses/`)

All loss modules are `nn.Module`s taking `(model_output, batch)`:

| Class | Task |
|---|---|
| `CrossEntropyLoss` | multiclass |
| `BinaryCrossEntropyLoss` | binary classification |
| `MAE`, `MAE_Var` | regression / heteroscedastic regression |
| `WassersteinLoss`, `WassersteinSigmaLoss` | distribution-aware ordinal targets |
| `WassersteinCrossEntropyLoss`, `WassersteinEntropyLoss` | Wasserstein-distance CE variants |

`norm_entropy_loss` (in `entropy.py`) is used internally by trackers to convert
probability distributions into scalar entropy scores. The `__init__.py` export
block is generated by `utils/build_helper.py`; don't edit it by hand.

## Metric trackers (`tracking/`)

Trackers accumulate raw outputs on CPU during steps, then compute task metrics
at report time. The base `MetricTracker` stores named tensors, supports
weighted metrics, prints a Rich results table, optionally exports stores to disk
(`export`, `export_loc`, used by eval), and clears between epochs.

Subclasses declare which stores they consume via `store_names` and override
`calc_metrics`:

| Tracker | For |
|---|---|
| `BinaryClassificationTracker` | binary tasks: ROC/PR curves, thresholded metrics |
| `ClassificationTracker` | multiclass |
| `OrdinalRegressionTracker` | ordinal citation bands |
| `HeteroscedasticRegressionTracker` | mean/variance regression heads |
| `RegressionTracker` | plain regression |

Supporting modules: `plot_funcs.py` (curve plots), `calc_metrics.py`,
`log_lrs.py` / `log_params.py` (MLflow logging helpers).

## Callbacks

Only one lives here today: `callbacks/isnan_async.py` halts training if a loss
goes NaN. NaN detection is not wired into the Engine automatically; strategies
or experiments must call it if wanted.

## Adding a component

1. New loss: add `src/training/losses/<name>.py`, then regenerate exports with
   the build helper.
2. New tracker: subclass `MetricTracker`, set `store_names`, override
   `calc_metrics`.
3. New strategy/task type: subclass `BaseStrategy`, define the batch and output
   protocols, implement the two step methods.
4. Wire all three from an experiment module in `src/config/experiments/`;
   nothing in the Engine needs to change.
